# G1 — Wave 1 integrated; walking skeleton (a)

Wave 1 (`U1.01` … `U1.10`), integrated by `U1.INT`. What the skeleton found, what was decided, what was patched,
what is still open.

Gate G0 froze the contracts. This gate is the first time they were all wired together and RUN: a real `RunEngine`
over a real `EffectJournal`, a real `EventWriter`, a real `Resumer`, a real temp-**file** `SqliteStateStore` and the
`FakeRuntime`, killed at every crash point the run hits and resumed by a second host. That is where the two defects
of §2 came from; neither is visible to a unit check, because neither lives inside one unit.

### What the skeleton actually asserts

One agent, one journaled tool call. The golden run reaches `COMPLETED` and records the crash points it hit:
`host.after-lease`, `transition.before-commit`, `transition.after-commit`,
`checkpoint.after-events-before-snapshot`, `tool.after-intent`, `tool.after-effect`, `tool.after-done` — eight
`(point, occurrence)` pairs. Each pair is then a case: host A is killed exactly there (a `SimulatedCrash`, which
`run()` rethrows without releasing the run lease, so the lock is left held by a host that no longer exists — §4, fix
round 2), host B recovers, **steals that lease with `fencingToken + 1`** and finishes, and the run must land on the
golden final state:

- `run.state === 'COMPLETED'`, `stop.reason === 'review-clean'`;
- **exactly one effect row per idempotency key, `state: 'done'`** — I4.1, whichever side of the crash performed it;
- **`perform()` executed exactly ONCE**, counted at the effect body's first statement and summed over host A and
  host B (`Skeleton.performs`);
- **gapless sequence** 1..n, and `runs.last_sequence` agreeing with it;
- **`verifyChain(runId, projectKey)` ok**, so the hash chain *and* every checkpoint anchor MAC verify;
- **the resumed run's lifecycle event stream is the golden run's**, event for event, in order (`lifecycleSpine`);
- **the run lock is still host A's** (hostId, pid, startToken) between the crash and host B, and host B leaves
  **exactly one `lock.stolen`** whose payload carries the dead row's `fencingToken + 1` — DESIGN 4.3 crash point #2's
  right-hand column, asserted instead of assumed;
- **exactly one `tool.completed`**, except after a crash at `tool.after-effect`, where the count is exactly ZERO (see
  §3, U1.10 D3); at most one `checkpoint.created` for the whole run; `run.resumed` exactly twice (one per host
  incarnation — the golden run has one);
- the file the tool wrote is on disk with the content the intent's own `verify` names.

**Fix round 1 rewrote the first and the sixth of those, and the reason is worth keeping.** The gate originally
claimed "exactly one `done` per effect key … never a second `perform()` of an effect already done" and asserted it as
`toolCalls.filter(c => c.status === 'done').length <= 1`. That assertion cannot see a re-execution: the world pushes
its `toolCalls` entry *after* `journal.run` returns, so a host killed inside the effect pushes nothing and a host
that wrongly re-performed a `done` effect pushes the same single row as one that replayed it correctly. The other
invariants are blind to it too — the effect is keyed, so a re-perform completes the SAME row; extra events are
appended legally, so the sequence stays gapless and the chain still verifies; the write is idempotent, so the file
is unchanged. Measured, not argued: a mutant journal that calls `spec.perform()` on the `already-done` branch passes
every assertion the gate shipped with, and fails three cases of the current one, on
`expect(skeleton.performs).toBe(1)` alone. Raised by the U1.INT reviewer.

The stream comparison is the second half of "same final state", which `expectSettled` never checked (it compared the
run against itself). Three families are excluded from it, each for a recorded reason and not for slack: `run.resumed`
/ `lock.stolen`, `checkpoint.created` (an optimisation — DESIGN 4.3 row 18 — so a host
killed after its last transition legitimately leaves a COMPLETED run with none; a crash at `transition.after-commit`
does exactly that), and the effect's own `tool.*` rows (a `done` reconciled by `Resumer` is completed by recovery, so
the replaying host emits no second `tool.completed` — U1.10 D3 — and a crash before the effect ran costs one extra
`tool.requested` when the next incarnation re-issues under the same key). Those families are then pinned by
count instead of by position. Everything else — every command, every state change, every phase boundary — is
compared exactly, which is what catches a phase re-entered after it completed or a `start` accepted twice.

**What the first two exclusions actually are, measured in fix round 2** (they were described from the armchair until
the U1.INT reviewer counted them, and one description was simply wrong): `run.resumed` is **not** "only a resumed run
has it". `RunEngine.run` calls `Resumer.recover()` unconditionally (G1-D1), so it is **one row per host
incarnation** — the golden run has one and every crash case has two. `lock.stolen` is emitted by the host that takes
a DEAD owner's run lease over, so the golden run has none and every crash case has exactly one. Both are now asserted
by count, in both directions (golden and crash), rather than assumed to be resume-only and left unobserved.

## 2. The defects found at this gate (none is inside one unit)

### G1-D1 — `RunEngine.run` and `Resumer.recover` both took the run lease, and fought over it

**Symptom, reproduced twice on the first run of the skeleton.**

- Fresh run: `run()` acquired the run lease, then called `deps.resume.recover(runId, host)`; recovery's step 3
  found the lock its own caller had taken a millisecond earlier, asked the sweeper whether the owner was alive —
  it was, it is the same process — and threw `conflict/run-host-alive`. The engine's fatal handler then marked the
  run **FAILED**, under the host that owns it. Every first run of a composed engine would have done this.
- After a crash: the lock belonged to the dead host A, so recovery *stole* it (fencing + 1) — out from under the
  loop that had just taken it. The next `E0` renewal answered `false` and the engine died with
  `conflict/lease-lost`.

**Why it is the gate's and not a unit's.** `U1.09` filed exactly this question (request R7: "confirm this call order
— lease acquired by the engine BEFORE `recover()` — is what DESIGN 4.4 actually wants, or file a counter-request").
No unit could answer it: `packages/core/src/engine/**` and `packages/core/src/resume/**` belong to two units, and
no test in either owned path composes the two. The skeleton is the first thing that does.

**Decided.** DESIGN 4.4 answers it, in `resume/index.ts`'s own words: step 4 (immutability) runs "BEFORE taking the
lease over … so a pin mismatch must never let this host start acting as the run's owner". Recovery therefore owns
the lease acquisition, and the loop takes the lease recovery left:

1. `RunEngine.run` calls `deps.resume.recover(runId, host)` **before** `deps.leases.acquire(…)`, and **outside** the
   fatal handler — a recovery that refuses means another host is driving this run, and marking it FAILED would be
   this host's last illegitimate act on a run it does not own.
2. `createLeaseManager(...).acquire` **adopts** the **run** lock, requested **`exclusive`** and held **`exclusive`**,
   whose owner is this exact host (same `hostId`, `pid` and `startToken`) instead of refusing it, keeping the
   **existing** fencing token — bumping it (a `stealLock`) would invalidate the lease the holder, i.e. us, is already
   writing with. The store is unchanged: `acquireLock` refuses "as long as a CONFLICTING row exists", and a row whose
   owner is this very process is not a conflicting one. Every other request falls through to the refusal below.

**Fix round 1 narrowed that branch, and it is the kind of hole a gate must not leave.** As first written it compared
`hostId`/`pid`/`startToken` only. `locksConflict` (`packages/persistence/src/contract.ts`) matches on `(scope, key)`,
so a **`shared`** request against an **`exclusive`** lock held by the same host is a conflict — and the branch adopted
it, handing the caller a `LeaseToken` for a lock it did not ask for. Either holder's `release()` then destroyed the
other's lease and the survivor's next `renew()` answered false, i.e. `conflict/lease-lost`. The same aliasing gave two
independent acquisitions of one run lease by one host the same `lockId` and the same fencing token, which is 0.2 I6
("one writer per run, fenced") lost inside a process. DESIGN 4.4 step 6 rebuilds the **project** lock as `shared`, so
the request is real; the only reason nothing hit it today is that `resume/index.ts` calls `store.acquireLock`
directly. The guard is now `scope === 'run' && mode === 'exclusive' && sole.mode === 'exclusive' && …`, and the
branch has three tests of its own (see below) instead of transitive coverage through the skeleton. Raised by the
U1.INT reviewer.

**And the branch is now tested where it lives.** It is a behaviour change to a PUBLISHED api — `createLeaseManager`
is exported from the `@cohorte/core` barrel — and the gate had shipped it with coverage only through
`tests/integration/skeleton`, which asserts the end state and never the lease. That is precisely how the `mode` hole
survived. `packages/core/test/durability/lease.test.ts` gains three cases: adoption returns the same `lockId` and the
**same** fencing token with still one row (and the adopted lease is live — one `release()`, row gone); a different
`pid`, a different `startToken` or a different `hostId` still throws `conflict/run-host-alive`; a `shared` request
against this host's own `exclusive` lock throws instead of adopting, on both the `project` and the `run` scope.

No contract, no signature and no exported name changed. Files: `packages/core/src/engine/index.ts` (U1.09),
`packages/core/src/durability/lease/index.ts` (U1.08). `docs/v3/requests/U1.09.md` R7 is closed by this.

**One consequence for a unit test, patched here.** `packages/core/test/engine/pause-cancel.test.ts`'s "the fallback
commit (no table row answers the stop)" case reached `commitFatal` by making the *resumer* throw. That path no
longer exists; the case now throws from `factCollector.collect`, the first port of the loop body proper, with the
run still IDLE — the same shape, through a port the loop really calls.

### G1-D2 — a `CommandAuthenticator.anchor` of one's own makes every anchor unverifiable

`StateStore.verifyChain(runId, key)` recomputes a checkpoint anchor with `base.computeAnchorMac` (PLAN PC-4: the one
function `security` and `persistence` share). A `CommandAuthenticator` that spells the MAC any other way produces
anchors that verify against nothing — `verifyChain` answers `{ ok: false, reason: 'anchor-mac' }`, and nothing else
in the tree notices, because no unit test calls `verifyChain` **with a key**.

The skeleton does, and that is how it was found. It uses `computeAnchorMac`. **No code was changed**: the one other
`anchor` implementation in the tree is `fakeAuthenticator()` in `packages/core/test/engine/fixtures.ts` (U1.09),
whose tests never verify a chain, so it is not wrong — it is merely not the store's. **For `U2.02`** (the real
`CommandAuthenticator`) and for anyone writing a fake: `anchor` **is** `base.computeAnchorMac`, and the cheap way to
prove it is one `verifyChain(runId, projectKey)` assertion.

### G1-D3 — the simulated crash RELEASED the run lease, so no crash case ever exercised a takeover (fix round 2)

Found by the U1.INT reviewer, and it is the one the skeleton was structurally unable to find: it excluded the
evidence. `run()`'s `catch` rethrew a `SimulatedCrash` immediately and set its "do not release" flag only on the
ordinary-error path — but **a `finally` runs even when the `catch` around it rethrows**, so the outer
`if (!released) await releaseQuietly(deps, lease)` handed the lock back for a host the test had just declared dead.

Measured consequence, before the fix: `store.listLocks({ scope: 'run' })` was `[]` after every one of the eight
crashes, so host B always found a FREE lock and `lock.stolen` occurred **zero** times in all eight streams. DESIGN
4.3 crash point #2 ("lease held by a dead `(pid, startToken)`" ⇒ "lease stolen with `fencingToken + 1` after a
liveness check") and `Resumer`'s `acquireOrStealRunLease` takeover branch had no coverage in the walking skeleton at
all. It could not be noticed from inside the gate, because `lock.stolen` is excluded from `lifecycleSpine` — for a
good reason — and nothing counted it. **An exclusion is a claim about a row; a gate that excludes a row must also
count it somewhere, or the exclusion becomes the place where evidence goes to die.** Three of this document's own
sentences and two of the skeleton's comments were false because of it.

**Fixed, in two halves.** `packages/core/src/engine/index.ts` (U1.09): the flag is set at the TOP of the `catch`,
before the `SimulatedCrash` rethrow, and renamed `releaseHandled` — "the outer `finally` has nothing left to do
about the lease", which is true both when this host released it and when it must never release it. And the skeleton
now PROVES the takeover instead of assuming it: between host A's rejection and host B, the run lock must still be
there with host A's `hostId`/`pid`/`startToken`; after host B, exactly one `lock.stolen`, whose durable payload
carries the dead row's `fencingToken + 1`. `lock.stolen` stays out of `lifecycleSpine` (it is genuinely resume-only)
and is pinned by count in both directions. `pnpm --reporter=silent unit:check U1.09` is green.

## 5. What `COHORTE_TEST_STORE=sqlite` found

Re-running the core durability / engine / resume suites against a real temp-file SQLite store (instead of the
in-memory default) is not a formality: it found one defect the memory store cannot.

**`packages/core/test/engine/command-matrix.test.ts` seeded an `ApprovalRecord` without `createdAt`.** The field is
REQUIRED (`packages/persistence/src/records.ts`), but the literal is cast `as never` as a whole, so its absence
typechecked; `MemoryTx.putApproval` stored the object as given, and SQLite answered
`NOT NULL constraint failed: approvals.created_at`. Fixed in the test (the record now carries `clock.now()`).

**Worth knowing for later waves:** a `Partial`-shaped `as never` cast on a store record hides exactly this class of
bug, and only the SQLite run surfaces it. The conformance suite runs against both stores, but a *test fixture* does
not. 207 tests, 14 files, green on SQLite after the fix.

**And the gate wrote the lesson and then broke it, four lines later.** `tests/integration/skeleton/support.ts` used
`as never` on two columns of its own seeded `RunRecord` (`specId`, `specSha256`) and double-cast the signed `start`
command through `as unknown as CommandEnvelope<'start'>`, so the skeleton proved the MAC but never the protocol
SHAPE. Both are gone in fix round 1: the branded spellings `as SpecId` / `sha256(…)` the rest of the tree uses, and
`base: Omit<CommandEnvelope<'start'>, 'auth'>` with no cast on the return — a payload or an actor the protocol does
not accept now fails `tsc -p tsconfig.tests.json`. Raised by the U1.INT reviewer. A cast that silences the type
checker on a frozen contract is worth exactly as much in a gate's test as in a unit's.

## 8. The exit check

```sh
export COHORTE_CHECKPOINT_DIR=<absolute dir outside the repository>
pnpm --reporter=silent verify && COHORTE_TEST_STORE=sqlite pnpm exec vitest run packages/core/test/durability packages/core/test/engine packages/core/test/resume && pnpm exec vitest run tests/integration/skeleton && node scripts/build.ts --out .build/gate-1 && node scripts/pack-check.ts .build/gate-1 && node scripts/checkpoint.ts G1
```

Run whole, in one shell, on a quiet tree. `export` on its own line, never a variable PREFIX on the `&&` list — a
POSIX assignment prefix scopes the variable to the ONE command it prefixes, so the prefix form hands it to `pnpm`
and `checkpoint.ts` still exits 2 (G0 §10 item 1 measured it). The one-line form `plan.json` now carries,
`COHORTE_CHECKPOINT_DIR="${COHORTE_CHECKPOINT_DIR:?…}" node scripts/checkpoint.ts G1`, IS a prefix on the single
command that reads it, and says what is missing instead of failing late (U0.G R5, applied — §4).
