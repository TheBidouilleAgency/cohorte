# Requests from U0.06

## R1 — the silent Biome stack overflow (U0.02 R1) has a fourth trigger, and it needs no Promise at all

- **Where:** `packages/persistence/src/conformance/state-store.ts`, `packages/persistence/src/memory/state-store.ts`,
  `packages/persistence/test/contract/types.test.ts` — the three files the lead's note named. Same symptom as
  `U0.02.md` R1 / `U0.03.md` R1 / `U0.07.md` R3: the native Biome binary aborts on a worker-thread stack overflow and
  the launcher (`node_modules/.bin/biome`, so `pnpm exec biome` too) **exits 0** with no `Checked N files` line:

  ```text
  $ pnpm exec biome ci packages/persistence packages/testkit ; echo rc=$?
  thread 'biome::workspace_worker_4' (…) has overflowed its stack
  fatal runtime error: stack overflow, aborting
  rc=0
  ```

  Reproduced on each of the three files individually, three runs out of three (macOS arm64, node 24.21.0, the pinned
  Biome 2.5.14). Every OTHER file this unit owns (all of `packages/persistence/src`, `packages/testkit/src/store-factory`)
  is clean: with the rule off (see below), `biome ci` reports `Checked 45 files … No fixes applied.` and exit 0.

- **The trigger, bisected with throwaway probe files inside `packages/persistence/src/memory/` (all deleted, never
  committed):** `MemoryTx` (`memory/state-store.ts`, the synchronous `StoreTx` implementation, ~345 lines, ~26
  methods) crashes Biome **on its own, with every `async`/`Promise` method of the file stubbed to a one-line body**.
  Conversely, with `MemoryTx` itself stubbed to trivial synchronous bodies and every real `async` method of
  `MemoryStateStore` left intact (the actual `Promise<...>`-returning methods `nursery/noFloatingPromises` is
  supposed to be checking), Biome does **not** crash. So triggers A/B/C already on file (`Static<TRecord>`, an
  unbound `await` of a value holding `ErrorInfo`) are not what's happening here: this crash needs no `Promise`,
  no `await`, and no floating-promise candidate anywhere in the crashing code — it is Biome's type-aware inference
  choking on the destructuring-rest / object-spread manipulation of the mutually-recursive `Record` types
  (`RunRecord`, `EffectRecord`, `EffectIntent`, `ApprovalRecord`, …) that `records.ts` / `contract.ts` define, once a
  single file has enough of that shape (a couple of hundred lines was not enough by itself in earlier probes; the
  full `MemoryTx` was). I could not pin it down to one method or one line within the time this unit budgets for a
  tooling bug that exits 0 either way; the strongest candidate by eye is `beginEffect`'s
  `const { runId, idempotencyKey, kind, replayClass, request, verify, ...optional } = copy(e);` followed by
  `{ …, ...optional, … }` into the `effects` map (rest-destructure of a union-shaped, mostly-optional type, then
  re-spread into a new object literal), but a probe isolating that one method timed out my budget before it produced
  a clean (non-parse-error) minimal repro.
- **Whether restructuring avoids it:** not conclusively. Splitting `MemoryTx` across more/smaller methods or files
  might well dodge whatever recursion bound Biome hits, but `MemoryTx` is fully tested (172 passing tests across the
  package) and dense on purpose (DESIGN 2.4: "stores are dumb"); I did not want to reshape working, spec-matched code
  to chase a tool crash that **does not fail the check either way** (see next point). Flagging as `lead` severity per
  the run note rather than guessing at a restructure.
- **What this means for U0.06's own check:** the literal `pnpm exec tsc -b && pnpm exec biome ci packages/persistence
  packages/testkit && pnpm exec vitest run packages/persistence` **passes, exit 0**, same as every other unit that
  has hit this bug — the crash exits 0 regardless, so it was never going to fail the `&&` chain. What it does cost is
  coverage: `noFloatingPromises` (and every other Biome check) never actually ran to completion on these three files.
  I verified the rest by hand, the way `U0.02`/`U0.07` record doing: a **throwaway** local Biome config (never
  written into the repo, `nursery.noFloatingPromises: "off"`, otherwise byte-identical to `biome.json`) turns the
  crash off and reports exactly two fixable diagnostics — one `lint/complexity/useOptionalChain`
  (`memory/state-store.ts:433`) and formatting drift in two files (`memory/state-store.ts`,
  `conformance/state-store.ts`) — which I fixed with `biome check --write --unsafe` under that same throwaway config
  (format/lint fixes only, no semantic change; confirmed by the still-green `tsc -b` and the still-172-passing
  `vitest run packages/persistence` afterward). With the rule off, the owned paths are `Checked 45 files … No fixes
  applied.`, exit 0 — no residual diagnostics.
- **Proposed change (tooling, same ask as `U0.02.md` R1):** treat the lint step as green only when the output carries
  Biome's `Checked <n> files` summary line and no `overflowed its stack` / `fatal runtime error`; until then a unit
  should read Biome's output, not its exit code, exactly as the three units before this one already found.
- **Affects:** the lead / whoever eventually owns a Biome upgrade or an issue filed upstream; no other unit imports
  these three files' internals (they are `packages/persistence/src/memory/**` and `src/conformance/**`, area
  subpaths, and a test file).

## R1b — fix round 1: the minimal repro of R1, five lines, and why restructuring is not the way out

The R1 reviewer asked for "the exact minimal construct that triggers it, and whether restructuring the code avoids
it". Bisected after the fix round (same tree, Biome 2.5.14, macOS arm64, node 24.21.0). **The whole file is this:**

```ts
import type { RunRecord } from '@cohorte/persistence/contract';
import { expectTypeOf, test } from 'vitest';
test('zones', () => {
  expectTypeOf<Record<never, never>>().toExtend<Pick<RunRecord, 'zones'>>();
});
```

```text
$ pnpm exec biome ci <that file>                              -> thread 'biome::workspace_worker_0' … has overflowed its stack   (exit 0)
$ pnpm exec biome ci --config-path=<noFloatingPromises off>   -> Checked 1 file in 1357µs. No fixes applied.                     (exit 0)
```

So the rule is confirmed as the trigger, and the construct is `Pick<…>` over an interface **imported from another
package** (source-first, so Biome infers it from the other package's `.ts`), consumed by a generic. Measured around it:

| Probe | Result |
|---|---|
| `Pick<RunRecord, 'zones'>` (a `string[]` key) / `Pick<RunRecord, 'plan'>` (a `RunPlan` key) in `toExtend` | **overflow** — the key does not matter |
| `toExtend<RunRecord>` (the whole interface, no `Pick`) | ok |
| `expectTypeOf<RunRecord>().toHaveProperty('pinnedInstallDir')` | ok |
| the same `Pick<…>` over an interface **declared in the same file** | ok |
| `const p: Pick<RunRecord, 'plan'> = {}; void p;` (no `expectTypeOf`) | ok |
| `const p: Pick<RunRecord, six keys> = {}; expect(p).toEqual({});` | **overflow** |

- **Does restructuring avoid it?** Not reliably, which is why nothing was reshaped for it. The last two rows are the
  answer: the same assertion rewritten as a plain value annotation crashes as soon as it grows, so the escape is not a
  code shape a unit can hold onto — and the type involved is the CONTRACT's own record type, so every test that pins
  the optionality of a run row's keys (exactly what `records.ts`'s six host-computed columns need) walks into it.
  `src/memory/state-store.ts` and `src/conformance/state-store.ts` are the same family (dense manipulation of those
  record types) and were not bisected further: the previous round already spent its budget there, and Biome exits 0
  either way, so it buys coverage, never correctness.
- **What that costs today:** `noFloatingPromises` and every other Biome check never run to completion on those three
  files. Verified by hand instead, with the throwaway config (never written into the repo, `vcs.enabled: false`,
  `nursery.noFloatingPromises: "off"`, otherwise byte-identical to `biome.json`): the unit's owned paths are
  `Checked 23 files … No fixes applied.`, exit 0 — no residual diagnostics after this round either.
- **Still asked of the lead, unchanged from R1 and from `U0.02.md` / `U0.03.md` / `U0.07.md`:** make the lint step
  honest (fail unless the output carries `Checked <n> files` and carries neither `overflowed its stack` nor
  `fatal runtime error`), then either set `nursery.noFloatingPromises` to `"off"` in `biome.json` or pin a Biome that
  does not overflow. The five-line file above is the upstream repro.
- **Affects:** every unit that writes a test over another package's record types — `U1.01` first (it writes the SQLite
  store against these very types).

## R5 — for U1.01: the four SQLite conformance failures this round exposed (all four are green again at hand-off)

The conformance suite is U0.06's and it is the contract; these were recorded, not fixed (PLAN §3 rule 1). U1.01 was
working in the same tree and its store answered all four before this unit finished, so nothing here is outstanding —
it is kept as the record of what the two new cases pin and of two defects that were not this round's doing. Two are
the fix-round findings the reviewer asked to pin, and every store must implement the same reading:

1. **`a run row may leave IDLE only with the six host-computed columns set`** — `patchRun(id, { state: 'PREFLIGHT',
   …HOST_COLUMNS, runtimePin: null })` resolved on SQLite and must reject with `StoreUsageError`. "Set" is
   **non-null**, as the DDL's `IS NOT NULL` CHECK reads it: `runtimePin?: JsonValue` makes an explicit JSON `null`
   well-typed, and writing it as the JSON text `null` satisfies `IS NOT NULL` while meaning "no runtime pin".
   `MemoryStateStore` now filters with `== null` (`src/memory/state-store.ts`), and the JSDoc of
   `HOST_COMPUTED_RUN_KEYS` (`src/records.ts`) states the rule.
2. **`a run-scoped transaction may rewrite its run but never create one`** — `putRun` of an unknown run inside
   `transact({ runId }, lease, …)` resolved on SQLite and must reject with `StoreUsageError`. Creation belongs to
   `transact('project', null, …)` alone, because that is the only transaction that also carries the signed start
   command (DESIGN 4.3 #1); a run-scope lease of a run that does not exist is legal (the lock table knows nothing of
   runs) but is not a second birth certificate.

And two that predated this round and were NOT caused by the suite change (both reproduced on their own with `-t`,
against test cases U0.06 did not touch):

3. **`only the RUN lease writes the run: another lock of the same run is not a licence to write it`** — a `zone`
   lease whose owner names the run was accepted by `transact({ runId }, zoneLease, …)`; it must throw
   `conflict/lease-lost` (I6: one writer per run, and the fencing assert is against the RUN lock).
4. **`the worktree ledger: one row per path, cleared up to an effect sequence`** — a deleted path round-tripped as
   `undefined` instead of `null`. `LedgerEntry.sha256` is `Sha256 | null` and the `null` is load-bearing (4.4: "null =
   deleted"); the SQL NULL must be read back as `null`, not dropped.

- **Affects:** U1.01. Nothing here changes an exported name or shape of U0.06's contract: `records.ts` and
  `contract.ts` are untouched apart from one JSDoc sentence.
