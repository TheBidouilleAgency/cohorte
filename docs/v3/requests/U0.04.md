# Requests from U0.04

Nothing here blocks U0.04 (its check is green). These are the points where DESIGN was silent or where another unit
is affected.

## R1 — `compileStrict` / `toOpenJsonSchema` take the events table as FIRST argument (information for U0.05)

- **Where:** DESIGN 2.3.2 writes `compileStrict(type)` and `toOpenJsonSchema()` (bound to the global `EVENTS`); PLAN U0.04
  asks for them "generic over an EVENTS table so U0.05 only adds rows", and `EVENTS` belongs to U0.05.
- **What U0.04 did:** `packages/protocol/src/compile.ts` exports `compileStrict(events, type)`,
  `compileStrictEnvelope(events, type)`, `toOpenJsonSchema(events)`, plus `bindCatalogue(events)` which returns the three
  with the EXACT DESIGN signatures. U0.05: `const catalogue = bindCatalogue(EVENTS)` — do not re-export functions named
  `compileStrict` / `toOpenJsonSchema` from the barrel a second time (the generic ones already carry those names).
- Type helpers for the catalogue are in `envelope.ts`: `EventDeclaration`, `EventTable`, `PayloadOf<E, T>`,
  `EnvelopeOf<E, T>` (= DESIGN's `Envelope<T>` over a table), `DurableTypeOf<E>`.
- **Authoring rules the generator relies on:** (1) `toStrictSchema` closes EVERY object that declares `properties`, so an
  author need not write `additionalProperties: false` (and `toOpenSchema` removes it where someone did, base's schemas
  included); (2) members of an `allOf` are NOT closed — do not author wire shapes with `Type.Intersect`, compose
  `properties` instead (see `compileCommand`); (3) open enums are `OpenEnum([...])`, closed ones `ClosedEnum([...])`
  (one `enum` keyword, no `anyOf` of constants), both in `open-enum.ts`.

## R2 — two names DESIGN uses without declaring them

- `OpenEnumOf<K>` (DESIGN 2.3.1, 2.3.3, 2.3.4): declared in `open-enum.ts` as `K | (string & Record<never, never>)`.
- `SchemaIssue` (DESIGN 2.3.2): declared in `compile.ts` as `{ path: string /* JSON pointer */; keyword: string; message: string }`.
- **Proposed change:** one line each in DESIGN 2.3.2.

## R3 — `ArtifactRef` is declared in `vocabulary.ts` and re-exported by `refs.ts`

- **Why:** `CheckResult` (vocabulary, DESIGN 2.3.1) needs `ArtifactRef` (refs, DESIGN 2.3.3) and `refs.ts` needs
  `ActivePipelineState` / `PipelineProfile`. Schemas are VALUES: an import cycle between the two files reads a const before
  it is initialised. Import it from either file; `export *` of both from the barrel is fine (same binding, checked with tsc).

## R4 — RESOLVED IN U0.04 (fix round 2): a published schema carries each cyclic definition ONCE, at the root (information for U0.G)

- **Was:** `@cohorte/base` `JsonValueSchema` / `ErrorInfo` are `Type.Cyclic` schemas, inlined by TypeBox at every use as
  `{ $defs: { JsonValue: { $id: 'JsonValue', … } }, $ref: 'JsonValue' }`. TypeBox compiles the repetition; ajv refuses two
  schemas with one `$id` (`reference … resolves to more than one schema`), so a schema-only client (AC-07) could not compile
  the published document as soon as a table used `JsonValue` twice.
- **Now:** `toOpenSchema`, `toOpenTableSchema`, `toOpenJsonSchema` and `toOpenCommandsJsonSchema` hoist every such definition
  to the ROOT `$defs` once, drop its `$id`, and rewrite the references to `#/$defs/<name>` (open mode only; the strict side
  is untouched). Two different definitions under one name throw. `scripts/gen-schemas.ts` has NOTHING to hoist.
- **One rule for callers:** the result of a `toOpen*` function is a whole DOCUMENT (its pointers are relative to its root).
  To publish a bigger document, compose the AUTHORED TypeBox schemas and call `toOpenSchema` once on the whole; do not
  embed an already published schema inside another one.
- Tested with `ajv/dist/2020` strict in `test/core/strict-open.test.ts` and `test/core/commands.test.ts`.

## R5 — envelope ids and instants use base's brand schemas (stricter than the DESIGN 2.3.2 listing)

- DESIGN writes `runId: Type.String({ pattern: ID_PATTERN })` and `timestamp: Type.String({ format: 'date-time' })`.
  U0.04 uses `RunId` and `IsoInstant` from `@cohorte/base` (`^run_[0-9a-f]{32}$`; RFC 3339 UTC with milliseconds), which is
  what DESIGN 2.1 says those brands are, what `parseId` enforces and what testkit `SeqIds` mints, and it gives the envelope
  branded static types. Same for `commandId`, `approvalId`, … in commands. Say so if the looser patterns were intended.


## R6 — static types of OPEN enums are wider than DESIGN's interfaces (information for every consumer of `PipelineProfile`)

- DESIGN 2.3.4 `start.profile: PipelineProfile` and 2.3.3 `RunPlan.profile: PipelineProfile` read as the closed union
  `'feature' | 'bugfix' | 'review'`. The wire is open (DESIGN 2.3.1, spec 32), so the schema is `OpenEnum(PIPELINE_PROFILES)`
  and the STATIC type of a parsed payload is `OpenEnumOf<PipelineProfile>`: the known literals for completion, any string
  accepted. `const p: PipelineProfile = cmd.payload.profile` or an exhaustive `switch` does not compile without a guard.
  The same holds for every other `OpenEnum` field (`Actor.transport`, `CohorteRole` on the wire, `ArtifactRef.kind`, …).
- **What a consumer does:** narrow at the door with `isKnownProfile(value)` (exported from `vocabulary.ts`, additive in fix
  round 2) or `PIPELINE_PROFILES.includes(...)`, and reject the unknown value there; `core` then switches exhaustively.
- No type was changed: the contract is published.

## R7 — how a second validator must be configured to compile a published schema (U0.G `scripts/schema-compat.ts`, DESIGN 2.3.2 / CI)

- DESIGN asks for `ajv/dist/2020` STRICT and also prescribes the custom keyword `x-cohorte-known`: ajv strict refuses an
  unknown keyword, and it refuses an unknown FORMAT too (`date-time` on `timestamp`). The configuration that works, and the
  one U0.04's tests use: `addFormats(new Ajv2020({ strict: true, keywords: [OPEN_ENUM_KEYWORD] }))` with `ajv-formats`
  (already in the root `node_modules`) and `OPEN_ENUM_KEYWORD` from `@cohorte/protocol` `open-enum.ts`.
- **Proposed change:** say so in DESIGN 2.3.2 / the CI section, and build the schema-compat Ajv that way.
