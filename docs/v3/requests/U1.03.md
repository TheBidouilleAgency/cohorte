## R3 — DESIGN 2.6.4's per-program re-targeting list should say it is illustrative (fix round 1)

- **Where:** DESIGN §2.6.4 `ProgramProfile.parse`'s interface comment and ADR-0024 item 4, both of which list
  re-targeting options for `git`, `pnpm`, `npm` and `node` only, after the normative sentence "Returns a denial
  for **any** global option that re-targets the command".
- **Why:** taken as a CLOSED set, the `yarn` and `docker` profiles carry no re-targeting options at all, and
  `yarn --cwd=<dir> install` / `docker --context=remote compose up` / `docker -H tcp://host …` parse exactly like
  the benign call (the `=`-joined form consumes no following token), so an ordinary allow rule matches and the
  RE-TARGETED command executes. That is the EV-08/09 mechanism `git -C` is denied for. The reviewer of fix round 1
  reproduced both as `allow`.
- **What U1.03 did:** followed the normative sentence, not the list: `YARN_RETARGETING = ['--cwd']` and
  `DOCKER_RETARGETING = ['-H', '--host', '--context', '--config']`, with EV-08/09 (bis) cases in
  `must-deny.evasions.test.ts`.
- **What U1.03 added in fix round 2** (same class, found by the second reviewer — exact functional SYNONYMS of
  options DESIGN does name, which parsed as benign globals): `GIT_RETARGETING` gains `--config-env` (the
  environment-variable form of `-c`), `--super-prefix` and `--attr-source` (both value-taking, so a benign parse
  also shifted the subcommand out from under the D9 check); `NODE_RETARGETING` gains `--experimental-loader`
  (Node's own documented alias of `--loader`), `--env-file` and `--env-file-if-exists`. Each has a row in the
  EV-08/09 (bis) table asserting `code === 'security/command-global-option'`, and each row's fixture rule lists
  the option in `flags.allow` so the row fails if the parse-time denial ever stops being the primary mechanism.
- **Proposed change:** one word in DESIGN §2.6.4 and ADR-0024 item 4 — "for example `git -C/-c/…`" — so the list
  reads as illustrative. If the lead wants it closed instead, that is a lead ruling and DESIGN should say so
  explicitly, because the current state of the closed reading is an allowed re-targeted execution.
- **Affects:** DESIGN/ADR wording only; the code is already on the safe side.

## R4 — two deviations recorded against DESIGN 2.6.4's matching contract (fix round 1)

1. **`subcommand` is matched as a PREFIX of the non-flag token stream, and an absent one is "no constraint".**
   The profile's structural `parse` emits a ONE-token `subcommand` (the first non-flag token) and puts every later
   non-flag token in `positionals`. Matching `rule.subcommand` by strict token equality therefore made DESIGN's own
   example (`subcommand?: readonly string[] // exact tokens, e.g. ['run','test']`) and every rule for a
   subcommand-less profiled program (`node`) silently DEAD — fail-closed, but invisible to the policy author.
   `matchesStructurally` now matches `rule.subcommand` as a prefix of `[...parsed.subcommand, ...parsed.positionals]`
   and checks the remainder as positionals; `['compose','up']` and `docker-compose up` stay equivalent.
   **Proposed change:** none needed to DESIGN — this makes the documented shape work as documented.
2. **A rule's `flags.allow` is applied to `parsed.globals` too.** DESIGN separates `globals` from `flags` in
   `ParsedCommand` but says of `flags` "anything not allowed is denied"; leaving globals out of the check meant
   `pnpm --silent run test` satisfied a rule written for `pnpm run test`, which fails OPEN (and became reachable
   for `exact` rules once deviation 1 landed). Benign globals are still PARSED as globals — `git --no-pager push`
   still has subcommand `push`, EV-08/09 — but a policy that wants to permit one now lists it in `flags.allow`.
   **Proposed change:** optional one sentence in DESIGN §2.6.4: "a rule's `flags` allowlist covers the parsed
   globals as well as the post-subcommand flags".
3. **A flag never narrows a `deny` or an `ask` rule** (fix round 2, second reviewer's blocker-class finding, and
   the necessary companion of item 2). "Anything not allowed is denied" is a rule about what may be PERMITTED:
   narrowing an `allow` rule by an undeclared flag fails closed, but narrowing a DENY rule fails open — the deny
   stopped matching as soon as any flag it had not declared was present, while a broader allow rule that did list
   that flag kept matching, so `deny > ask > allow` (step 5) was defeated by one token. With
   `allow{pnpm run <test|build>, flags.allow ['--silent']}` + `deny{pnpm run build}`, all three of
   `pnpm run build`, `pnpm --silent run build` and `pnpm run build --silent` now return the deny. `flagsMatch`
   therefore applies the allowlist to `decision: 'allow'` rules only; `ask` is included because an ask shadowed by
   a broader allow is the same evasion one step weaker. Consequence for policy authors: a `deny`/`ask` rule
   matches on program + subcommand prefix + positionals alone, and a `flags` block on such a rule is inert.
   **Proposed change:** one sentence in DESIGN §2.6.4 making the direction explicit ("the `flags` allowlist
   narrows an `allow` rule only"), or, if the lead prefers flag-specific denies, a separate rule field that
   WIDENS rather than narrows (e.g. `flags.deny` as "match when present") — a contract change U1.03 did not make.
4. **`enum` and `paths-in-worktree` positionals have a lower bound of one** (fix round 2, minor finding).
   `every()` over an empty array is vacuously true, so a rule written for `pnpm run test` also matched the bare
   `pnpm run`, and one for `git add <paths>` the argument-less `git add`: every such rule was silently wider than
   its author wrote it. `none` and `exact` already pin the count. Consequence for policy authors: a rule that
   should also permit the zero-positional form needs a second rule (or `exact`/`none`).
- **Affects:** whoever authors the built-in / fixture `CommandRule` data (U2.01, the config schema's examples,
  the E2E fixtures): a rule for a command invoked with a global option must list that option in `flags.allow`;
  a `deny`/`ask` rule must not rely on a `flags` block to stay narrow; a value-bearing positional rule no longer
  covers the bare form.

## R5 — the D9 agent git deny must not depend on caller-supplied `profiles` (fix round 2, information)

- **Where:** `packages/security/src/decide/commands/index.ts` `evaluate()`, ADR-0007 item 2 / DESIGN 2.6.4 step 3.
- **Why:** the D9 check (`git commit|push|merge|…`) was nested inside "a git `ProgramProfile` was found", and
  `CommandPolicyOptions.profiles` is a public, caller-supplied option of this unit's own API — so
  `createCommandPolicy({ profiles: [] })` plus an exact-argv allow rule turned a NON-OVERRIDABLE invariant off.
- **What U1.03 did:** hoisted the check out of the profile branch; it now runs for every call whose canonical
  program name is `git`, after the structural parse (so a re-targeting global is still reported as
  `security/command-global-option`, the earlier and more precise verdict) and before rule matching. With a parse
  in hand the subcommand is `parsed.subcommand[0]`; WITHOUT one (a caller supplied `profiles` without git)
  nothing can tell a subcommand from a global option's value, so every token of `argv[1..]` is held against
  `AGENT_GIT_DENIED_SUBCOMMANDS` — conservative in the only safe direction for an invariant that must not be
  switchable off, at the cost of denying a hypothetical `git log --grep commit` for a caller who removed the git
  profile (the built-in profiles are the default and are unaffected).
- **Proposed change:** none to DESIGN. If an integrator would rather the invariant not depend on a caller's
  option list at all, the cleaner contract is to drop `profiles` from `CommandPolicyOptions` (it exists for
  tests) or to merge caller profiles OVER the built-ins instead of replacing them — a contract change, so not
  U1.03's to make.
- **Affects:** anyone constructing `createCommandPolicy` with an explicit `profiles` list (only this unit's own
  tests, today).
