# Requests from U1.05 (git: hardened runner, worktrees, tree digest, trailers, plumbing merge, review refs)

Filed during fix round 2. Nothing here blocks the unit: every item is implemented inside `packages/git/src/impl/**`
and `packages/git/test/impl/**`. They are recorded because a later unit (`U3.04` worktrees + provision, `U3.07`
commit/merge) or an integrator has to know.

## R1 — `GitPortOptions.worktreeRoot` is required (new field, unit-owned)

- **Where:** `packages/git/src/impl/context.ts`. `GitPortOptions` is the constructor argument of `createGitPort`;
  it is NOT part of the frozen `GitPort` contract, so this is not a contract amendment.
- **Why:** PLAN's deliverable and DESIGN 5 both say `resetHardClean` "refuses any path outside the worktree root",
  and DESIGN 5.1 says "every worktree path is canonicalised and must resolve under the root". Round 1 only
  checked that the target was a registered, non-main worktree of *its own* repository — self-referential, since
  `git worktree list` was run from the target: any linked worktree of any repository on the machine was accepted
  and hard-reset + `clean -fdx`. The guard needs the configured root, so the port must be given it.
- **Consequence for `U3.04`:** `createGitPort({ ..., worktreeRoot })` must be passed the CANONICALISED
  `git.worktreeRoot` of the run's project (`~/.cohorte/worktrees/<projectKeyId>/` or the configured override,
  after `configuration/worktree-root-protected` has accepted it, ADR-0021 §1). It is required, not optional: a
  port built without a root would have nothing to refuse against.

## R2 — `switchToNewBranch` now REFUSES a dirty slot (`WorktreeDirtyError`)

- **Where:** `packages/git/src/impl/worktrees.ts`; the error class is re-exported from `src/impl/index.ts`.
- **Why:** `git checkout -b <branch> <at>` carries the previous agent's uncommitted and untracked files onto the
  incoming agent's brand-new branch, so the next `commitAll` attributes them to the new agent and the ownership
  audit (5.3 b) only notices when the leftover happens to fall outside its write globs. DESIGN 5.2 / ADR-0021 §3
  say the branch is created AT the integration head; silently inheriting work contradicts that.
- **Consequence for `U3.04`:** at slot acquisition, a slot that is not clean must be quarantined
  (`resetHardClean`) — or the leftover committed — before `switchToNewBranch`. Ignored files (a provisioned
  `node_modules`) do NOT count as dirty: the check is `status --porcelain=v2 -z --untracked-files=all` without
  `--ignored`, the same predicate `removeWorktree` uses.
- **Proposed DESIGN change (optional, one sentence in 5.2):** "`switchToNewBranch` refuses a dirty slot; the
  caller quarantines it first."

## R3 — DESIGN 5.1's root rule is enforced here only for `resetHardClean`

- `addWorktree` does not refuse a path outside `worktreeRoot`: it creates whatever path the caller asks for. The
  destructive method is guarded because that is what PLAN and DESIGN 5 name; deciding WHERE a slot lives is the
  slot allocator's job (`U3.04`), and that is where "every worktree path is canonicalised and must resolve under
  the root" should be enforced for creation. If the lead prefers the guard on both, say so and it is four lines
  plus the test fixtures — but then every caller of `addWorktree` must site its worktrees under the root, which
  the current tests (and the `_review-<n>` detached slots) would have to respect.

## R4 — the `addWorktree` serialisation is in-process only (information)

- The per-repo queue in `worktrees.ts` protects ONE host process from itself (git's `.git/worktrees/` admin-area
  race, reproduced on this toolchain). DESIGN 5.6 takes the `project` lock SHARED, so two host processes can run
  on one repository; their `worktree add`s are serialised by that lease, not by this Map. The comment now says so.
  No retry-on-race loop was added: it would need a fixture that pre-creates a half-written admin directory, and
  the cross-process case is already covered by a lock the caller holds.

## R5 — this unit's tests are `*.itest.ts` (DESIGN 7.2)

- DESIGN 7.2 puts this unit's test list ("concurrent `worktree add`, exact porcelain match, tree digest E1-E9,
  `mergeTree` + conflict, `updateRefCas` race, review-ref immutability, hook canary (S-70)") in `git/test/*.itest.ts`.
  Round 1 named them `*.test.ts`, so they ran in the `unit` project (`pool: threads`, 5 s timeout) although they
  spawn real `git` and create worktrees. They are now `packages/git/test/impl/*.itest.ts`, collected by the
  `integration` project (`pool: forks`, 30 s). `ownedPaths`, `testPaths` and `tsconfig.checks/U1.05.json` are
  unchanged — no plan edit is needed.

## R6 — `facts().defaultBranch` implements 5.1's "else local `<default>`"

- `refs/remotes/origin/HEAD` exists only after a `clone` (not `--single-branch`) or an explicit
  `remote set-head`, so round 1 returned `null` for nearly every real repository, and its fallback
  (`config --get init.defaultBranch`) is unreachable under the hardened runner (5.0 forces
  `GIT_CONFIG_GLOBAL=/dev/null` + `GIT_CONFIG_NOSYSTEM=1`; that key is in practice global). The chain is now
  `origin/HEAD` -> local `main` -> local `master` -> the current branch when HEAD is a branch -> `null` (bare or
  unborn). If DESIGN wants a different local order, this is the one place to change.
