# Requests from U0.01

## R1 — `pnpm -s <script>` does not run under pnpm 12.4.2: respell it in PLAN.md and plan.json

- **Where:** `docs/v3/PLAN.md` (§4 table, every "Done when" that uses it, the W0 exit check) and the
  matching `check` / `exitCheck` / `conventions` strings of `docs/v3/plan.json`: 69 occurrences in
  plan.json (`unit:check` 51, `verify` 13, `legacy:test` 2, `ci:local` 2, `test:live` 1), 72 lines in PLAN.md.
- **Why:** pnpm 12.4.2 (the pinned `packageManager`, and what is installed on this machine) rejects the
  short flag before a script name:

  ```text
  $ pnpm -s legacy:test
  error: unexpected argument '-s' found
  Usage: pnpm [OPTIONS] <COMMAND>          (exit 2)
  ```

  `pnpm run -s <script>` is accepted but means `--sequential` there, not silent. This is the ONLY step of
  U0.01's "Done when" that is red, and it is red before the script starts. Every parallel unit's check
  begins with `pnpm -s unit:check`, so every unit would hit it.
- **Proposed change:** replace `pnpm -s ` by `pnpm --reporter=silent ` everywhere (documented in
  `pnpm --help`; arguments after the script name are passed through: verified with
  `pnpm --reporter=silent unit:check U0.01`). `pnpm --silent <script>` also works but is not in the help.
- **Meanwhile:** nothing in the tree depends on the spelling; the root scripts are named exactly as the
  plan says. U0.01 ran its check with the last step as `pnpm --reporter=silent legacy:test` (green) and
  reports the literal command as red.
- **Status after fix round 1:** still open. The independent reviewer reproduced it and confirmed that
  nothing in U0.01's owned paths can fix it; with the last step respelled, U0.01's whole "Done when"
  exits 0 (also from a clean clone after `pnpm install --frozen-lockfile --offline`).
- **Status after fix round 2:** still open, and it is the ONLY red step of U0.01's literal check. The second
  reviewer classed it as a blocker for the LEAD ("there is nothing to fix in its paths"). Looked at once
  more from U0.01's side, in an empty throwaway project: `pnpm -s hello` exits 2 with and without an
  `.npmrc` (`reporter=silent`) and a `pnpm-workspace.yaml` beside it, so no file U0.01 owns makes the
  spelling work; `pnpm -s run hello` IS accepted but is not silent (it prints `$ echo hi`);
  `--reporter=silent`, `--loglevel=silent` and `--silent` all work before a script name; `packageManager`
  is pinned to 12.4.2 by the plan. It is a pure string replace (`pnpm -s ` -> `pnpm --reporter=silent `)
  in `docs/v3/plan.json` and `docs/v3/PLAN.md`; no `ownedPaths` change, so `tsconfig.checks/**` stays in
  sync and `scripts/test/gen-unit-checks.test.ts` stays green. **Do it before U0.G / Wave 1**: every
  parallel unit's check starts with that spelling.
- **Affects:** every unit.

## R3 — DESIGN 1.2 net 1 overstates what pnpm strictness catches (information, no change needed)

- **Where:** DESIGN §1.2 "pnpm strictness. A workspace package resolves only if declared in the importer's
  `package.json`", and the U0.01 test wording "an edge absent from the table does NOT resolve".
- **Why:** PLAN PC-9 puts every `@cohorte/*` package in the ROOT `devDependencies`. Node resolves by walking
  up, so `@cohorte/core` resolves from `packages/base` through `<root>/node_modules` (verified). The
  statement holds for third-party names (the root declares none of `typebox yaml commander picomatch` or
  Pi), not for workspace names.
- **What U0.01 did:** `resolve-edges.test.ts` asserts, for an absent WORKSPACE edge, that nothing is linked
  in the importer's own `node_modules` (what pnpm controls), and for an absent THIRD-PARTY name that Node's
  resolver really fails. To close the hole, `check-layers` also checks `@cohorte/*` imports under
  `test/**` against `normal ∪ typeOnly ∪ dev` (rule a), in addition to `src/**`. `tsc -b` does NOT cover
  `src/**` for this case (R5): `check-layers` is the only net. Documented in `docs/v3/workspace.md`.
- **Affects:** any unit whose tests import a workspace package that its package does not declare: it runs
  under vitest but fails `check-layers` at the gate. The fix is a `dev` edge request, not a relative import.

## R5 — DESIGN 1.2 net 2 promises a TS6307 that `tsc -b` never emits for a workspace import by name

- **Where:** DESIGN §1.2, the paragraph before the port table ("`tsc -b` over the project references fails
  on a cycle (TS6202) and on an undeclared edge (TS6307)") and net 2 ("`tsc -b` fails on an undeclared edge,
  TS6307, and on a cycle, TS6202").
- **Why:** measured with TypeScript 7.0.2 on a mirror of the real configuration
  (`scripts/test/reference-net.test.ts`, found by the U0.01 reviewer). Exports are source-first and the
  root declares every `@cohorte/*` package (PC-9), so an import BY NAME of a package the importer does not
  reference resolves through a `node_modules` symlink to that package's `.ts` sources; TypeScript treats
  them as an external library, compiles them into the IMPORTER's program and reports nothing (exit 0).
  Same result for a `devDependencies`-only edge (`core -> runtime-fake`, anything `-> testkit`) imported
  from `src/**`. What `tsc -b` does refuse: a reference cycle (TS6202) and a RELATIVE import into another
  package (TS6059 + TS6307).
- **Consequence:** for an undeclared or dev-only workspace import from `src/**`, `check-layers` (rules a
  and d) is the ONLY net, not one of three.
- **What U0.01 did:** corrected `docs/v3/workspace.md`, the comments of `resolve-edges.test.ts` and
  `packages/core/test/canary.edges.test.ts`; pinned both columns in `reference-net.test.ts` (it fails
  with an explicit message if a later TypeScript starts refusing the import); made `unit:check` run
  `check-layers` (R6).
- **Proposed change:** in DESIGN §1.2 replace both sentences by: "`tsc -b` fails on a reference cycle
  (TS6202) and on a relative import into another package (TS6059/TS6307). It does NOT refuse an import by
  name of an unreferenced workspace package (source-first exports reached through `node_modules`): that
  case is caught by `check-layers` alone." No compiler flag was found that closes the hole:
  `preserveSymlinks: true` was measured on the same mirror — the undeclared import still builds (exit 0),
  and declared edges stop being read from `dist-types/*.d.ts` (they resolve to sources through the
  symlink as well), so it makes net 2 weaker, not stronger. The verified toolchain flags are unchanged.
- **Affects:** DESIGN only; every unit benefits from R6.

## R6 — `unit:check` has a fourth, read-only step; `tsconfig.tests.json` includes two more patterns

- **Where:** PLAN §4, row `unit:check` ("(1) tsc … (2) biome check … (3) vitest run …"), and PLAN PC-10 /
  the U0.01 deliverable that lists the `include` of `tsconfig.tests.json`.
- **What U0.01 did (fix round 1, on the reviewer's recommendation):**
  - `scripts/unit-check.ts` runs `checkLayers()` in process between Biome and vitest (about 50 ms, reads
    only). A violation located in a file the unit owns makes the check RED; a violation anywhere else is
    printed as a warning, exactly like a foreign tsc diagnostic. A tree without `layers.json` skips the
    step and says so. `--self-test` has a fifth scenario for it.
  - `tsconfig.tests.json` also includes `vitest*.config.ts` and `apps/*/*.config.ts`: root-level and
    app-level config files are in no composite project (`include: ["src"]`), so after their wave nothing
    typechecked them (`apps/cli/tsdown.config.ts` of U0.10 is the next one).
- **What U0.01 did (fix round 2, on the second reviewer's finding):** the "no test file matched" guard was
  all-or-nothing over the whole `testPaths` list — `vitest run a b` is green as soon as ONE path selects a
  file. On the Wave-0 tree `unit:check U0.02` was GREEN with nothing written: U0.01's canary under
  `packages/base` satisfied the guard for `packages/testkit/test/foundation`, which did not exist. Every
  unit whose `testPaths` include `packages/base`, `apps/cli` or a `tests/<suite>` root had the same hole.
  - Before `vitest run`, the test step calls `vitest list <testPath> --filesOnly --json` once per path
    (same env, same private cache dir, about 130 ms each, executes nothing) and FAILS, naming the path,
    when a path selects no file on its own. A file-name prefix such as `…/tripwires/tw-` (U4.08) works:
    vitest itself reads the filter.
  - From the same listings: a file under the `testPaths` named `*.test.ts`, `*.itest.ts` or `*.e2e.ts` that
    NO vitest project collects (a `*.e2e.ts` inside a package, an `*.itest.ts` under `src/`, a `*.test.ts`
    under `tests/`) never runs. It FAILS the check when the unit owns it, and is a warning otherwise. Any
    other test-looking name (`*.spec.ts`, a `.tsx` / `.mts` / `.js` extension) only ever WARNS, because it
    may be fixture data. No file named in PLAN.md or DESIGN.md is affected (checked: every planned test
    file sits where its project collects it). `*.live.ts` is not concerned.
  - `--self-test` has two more scenarios, `scripts/test/unit-check.test.ts` three more cases.
- **Consequence for a unit:** every entry of its `testPaths` must select at least one test file when the
  unit is done. A unit that ends up with no test in one of its declared directories asks for the plan entry
  to be changed (this file's siblings), it does not leave the directory empty.
- **Proposed change:** PLAN §4 row: "(3) `check-layers`, read-only: violations in owned files fail, others
  warn; (4) `vitest run` …; non-zero when no test file matched, when ONE of the `testPaths` selects no file,
  or when an owned `*.test.ts` / `*.itest.ts` / `*.e2e.ts` is collected by no vitest project"; the same
  sentence in `conventions.unitCheck` of `plan.json`; PLAN PC-10 / U0.01 deliverable: add the two patterns
  to the list.
- **Affects:** every unit, favourably: a layering violation, a test directory that was never written and a
  test that can never run all show up in the unit's own check.

## R7 — `check-layers` reads two more things than DESIGN 1.2 lists (information, no change needed)

- **Where:** DESIGN §1.2 net 3, rule g ("`import(` outside `apps/cli/src/lazy.ts` …") and the L0-L5 diagram.
- **What U0.01 did (fix round 2):**
  - Rule g also refuses the identifier `createRequire` in shipped code outside the same two files: it is
    the same lazy load under its CommonJS name, and with a computed specifier it was invisible to every
    rule. The scanner now also reads `` import(`x`) `` (a template without `${}` is a string literal),
    `createRequire(…)('x')` and `load('x')` where `load` is bound to `createRequire(…)`, so rule b sees a Pi
    load in `apps/cli/test/**` — the one place outside the child where Pi resolves.
  - `layers.json`'s `layer` field is no longer decoration: `validateLayers` (run by `loadLayers`, so by
    `check-layers` and `unit:check`) refuses a `normal` / `typeOnly` edge that does not go DOWN `L0..L5`,
    a same-layer edge outside `L2` (so no `L1 -> L1`, rule C4), and a non-`dev` edge into the `dev` layer.
    The current data passes unchanged.
- **Proposed change:** optional, DESIGN §1.2 rule g: "`import(` or `createRequire`". DESIGN 3.9 already
  obtains Pi's install path through `import.meta.resolve`, which rule g does not touch.
- **Affects:** an integrator who edits `layers.json`; a unit that wanted `createRequire` in shipped code
  (none is planned) asks for an entry in `rules.g.allowedIn`.
