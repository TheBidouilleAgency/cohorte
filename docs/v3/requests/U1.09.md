## Informational (no dependency change; recorded for whoever reads the engine next)

- **Checkpoint is two `store.transact()` calls, not one.** DESIGN 4.2's `tx { run.state.changed ; stop ;
  checkpoint.created ; writeSnapshot }` reads as one transaction, but crash point #18
  (`checkpoint.after-events-before-snapshot`, "on disk: events without the new snapshot") can only exist if the
  checkpoint EVENT already committed, durably, before the crash — which needs its own, already-committed
  transaction. `packages/core/src/engine/checkpoint.ts`'s `writeCheckpoint` does exactly two: one for
  `checkpoint.created`, the crash point, then one for `tx.writeSnapshot`.
- **A `SimulatedCrash` (or a real `SIGKILL`, which never reaches a catch) is rethrown unchanged** by `run()`'s
  top-level catch, never turned into a `commitFatal` — otherwise every crash-point test would observe a graceful
  `FAILED` commit instead of the engine "dying" where it says it does. Only a genuinely unexpected throwable reaches
  `commitFatal` (DESIGN 2.8: "unknown throwable ⇒ FAILED + checkpoint.created{cause:'fatal'}"), which reuses `T26`
  (`*active -> FAILED`) through the SAME `settleStop` machinery as a global stop when the run is in an active state
  that row can fire from, and falls back to a direct `patchRun` otherwise (e.g. a throw while still `IDLE`).
- **`command.external.after-accepted` (DESIGN 4.3 #19, named for "cancel/shutdown") is also hit for `pause`.**
  DESIGN 4.6 gives pause the same "durable flag first" shape cancel has ("command.completed for a pause is emitted
  when PAUSED is committed, not when the request is received"), so this engine crash-points there for both.
- **No `waiting`/idle `StopReason` exists in DESIGN's closed set.** When a pass finds no pending command, no open
  phase and no global stop (e.g. a run genuinely idle, waiting on a client), `run()` sleeps
  `pollIntervalMs`/`DEFAULT_POLL_INTERVAL_MS` (default 250 ms, DESIGN 4.7) and loops back to E0 rather than
  returning — this is why `RunEngineDeps.pollIntervalMs` exists (tests set it small).

## Fix round 1 — what changed, and the two new requests it raises

The independent reviewer's blockers and majors are all addressed inside this unit's `ownedPaths`
(`packages/core/src/engine/**`, `packages/core/test/engine/**`). The public contract is unchanged: `createEngine`,
`RunEngineDeps` and `drainInbox` keep the names and shapes they were published with. Two exports were ADDED
(`packages/core/src/engine/commands.ts`, and `resumeToFor` / `runEffects` from `transitions.ts`); `TableLookup` is
now re-exported from `pipeline/tables/index.ts` instead of re-declared, so the type identity is unchanged for any
importer.

- **`resumeTo` on a command-driven suspension.** `resumeToFor(from, to)` (transitions.ts) is now the ONE rule both
  the stop ladder and the command path apply — "an active state was left for one that is not". A `pause` command
  therefore records `resumeTo` in the run row AND in the `run.state.changed` payload, and the next `resume` resolves
  `*resumeTo` instead of throwing `corruption/projection-mismatch`.
- **Human-actor stop rows (T20, T27).** A durable `pauseRequested` / `cancelRequested` flag is only ever written in
  the accept transaction of a verified command, so it IS the trace of one. `settleStop` now looks the still-`claimed`
  command up and fires the row with THAT command's normalised actor and `commandId`, clears the flag and completes
  the command (DESIGN 4.3 #19); `assertNotHumanActor` still refuses a human row with no such command behind it (both
  cases are tested). `drainInbox` additionally recovers such a command BEFORE E2 ever sees the flag, which is what
  makes a fresh engine finish a cancellation instead of reaching `checkGlobalStops` at all.
- **The flag is written only when the matrix applies the command.** The matrix cell is resolved BEFORE the accept
  transaction; a `reject` or `noop` cell (`pause` on IDLE/FAILED/BLOCKED/COMPLETED, `pause` on an already-suspended
  run, `cancel` on a terminal run) never sets it.
- **`expectedSequence`** is compared against `runs.lastSequence` read BEFORE the accept transaction, so a client that
  sends the sequence it last observed is accepted.
- **One transaction per command.** Every command is PLANNED (reads only) and then applied in a single
  `store.transact` — `{ claimCommand ; command.accepted ; the command's events ; command.completed|rejected ;
  finishCommand }` — including rejections, `{noop}`s and `approve`/`deny`. Only `pause`/`cancel` keep the two
  transactions DESIGN 4.2 E1 allows for an external effect, and `drainInbox`'s recovery closes that window.
- **`approval.resolved`'s real sequence** is now stored in `ApprovalDecisionRecord.resolvedSeq` (it was `0`).
- **Transition effects run AFTER the commit** (DESIGN 4.2: E5 the transaction, E6 the effects) and are skipped when
  the idempotency key answered `'duplicate'`. The ONE exception is DESIGN 4.6's pause/cancel shape, where the durable
  flag is already committed and the effects must run between it and the final state commit.
- **`run.paused` / `run.cancelled` + a checkpoint** are emitted by a command-driven pause/cancel (DESIGN 4.6).
- **The run lease is released** on every non-crash exit of `run()`.
- **Tests**: `packages/core/test/engine/inbox-tx.test.ts` (new: `expectedSequence` both ways, no stuck flag on
  reject/noop, one-tx counting), a pause→resume with NO pre-seeded `resumeTo`, both `settleStop` human-row cases, the
  `command.external.after-accepted` crash point with its own golden run, and `skip`'s landing state (the matrix test's
  `transition-per-phase` branch, previously dead).

### R9 — `StateStore` has no reader for `claimed`-but-unfinished commands

- **Where:** `packages/persistence/src/contract.ts` — `pendingCommands(runId)` returns `status: 'pending'` only,

  status filter) to `StateStore` at the next persistence revision; this engine then drops the journal scan.
- **Affects:** `U1.01`/`U0.06` (the stores) and the real `Resumer`, which needs exactly the same reader.

## Fix round 2 — what changed

The second reviewer's two blockers, one major and three minors are all addressed inside this unit's `ownedPaths`
(`packages/core/src/engine/**`, `packages/core/test/engine/**`). The published contract is unchanged: every exported
name (`createEngine`, `RunEngineDeps`, `drainInbox`, `settleStop`, `closePhaseAndAdvance`, `makePhaseRunId`,
`resumeToFor`, `runEffects`, `hostComputedColumnsForStart`) keeps its name and shape. ONE export was added,
`nextPhaseIteration` (transitions.ts), and one optional trailing parameter (`stop`) to a module-private helper.

- **A suspended or halted run ends the loop (blocker).** `run()`'s gate tested only the two TERMINAL states, so a
  `pause` the drain had just applied fell through to `findOpenPhase` + `deps.phases.execute`: a pause never closes
  the phase row, so the still-open phase was re-executed and `closePhaseAndAdvance` then found no row answering a
  `passed` outcome *from PAUSED* and drove the run to FAILED — a pause destroyed the run. The gate is now
  `NO_SCHEDULING_STATES` = terminal ∪ halted ∪ suspended (DESIGN 4.6: "the engine schedules nothing new"; every one
  of those states is left by a COMMAND sent to a freshly spawned host, DESIGN 4.7). IDLE is deliberately excluded:
  a run waiting for its own `start` keeps polling.
- **A command-driven pause/cancel records its `StopRecord` (same blocker, second half).** `applyExternal` now patches
  `stop` on the run row AND carries it in the `run.state.changed` payload — exactly as `settleStop` already did for
  the stop ladder, so `RunState.run.stop` says the same thing read from the row or replayed through `evolve()`, and
  `run()` answers a paused run with `{reason:'paused'}` instead of the `review-clean` default. `finalStopRecord`
  additionally maps every end state to the `StopReason` it stands for (DESIGN 2.5.3's table read backwards) for a run
  that reached that state without one.
- **The phase iteration is computed, not hard-coded (blocker).** `nextPhaseIteration(runState, state)` =
  "how many phase rows of this state exist, + 1", used by `closePhaseAndAdvance` and by the inbox's
  `prepareTransition`. With a fixed `1`, every revisit of a phase reused `phs_<STATE>_1` (overwriting the earlier
  row) AND produced the same transition idempotency key for two firings of the same row, so the second firing was
  rolled back as a `'duplicate'`, the phase stayed `running`, and the engine re-executed it for ever: the shipping
  `feature@1` FIX loop (TEST → FIX → TEST) was unexecutable. New regression test
  `packages/core/test/engine/phase-iteration.test.ts` drives a looping toy table through two red TEST rounds and
  asserts six distinct phase rows, two `L-RED` transitions and pairwise-distinct idempotency keys.
- **The fatal fallback journals what it does (major).** `commitFatal`'s unconditional branch moved the run to FAILED
  with a bare `patchRun`: no `error` event (DESIGN 2.8) and no `run.state.changed` (DESIGN 4.2), so the row and the
  journal disagreed and no observer ever learned the run had failed. It now appends both drafts in the SAME
  transaction as the patch. Nothing is written to `transitions`: no table row fired, and `recordTransition` is the
  register of rows that did — the event's `defId` is the literal `fatal` (no table row is named that) and its
  idempotency key uses the same marker, so neither can be mistaken for a row.
- **`settleStop` leaves the same journal as the inbox path (minor).** When the stop it settles was caused by a
  claimed `pause`/`cancel`, it now emits `run.paused` / `run.cancelled` before `run.state.changed` (DESIGN 4.6 tx2
  lists them for both paths); `stateChangedIndex`/`within` follow the real draft positions.
- **The command-matrix test asserts the rejection CODE (minor).** For every `reject` cell it reads the
  `command.rejected` event and compares `error.details.matrixCode ?? error.code` with the cell's own code — which
  pins the five uncatalogued codes of R3 today and keeps passing the day the catalogue gains them.
- **`HarnessOptions.table` is honoured, not dead (minor).** `makeHarness` resolves it for every `(profile,
  tableVersion)` when no explicit `resolveTable` is given; `phase-iteration.test.ts` is its first user. The fixture
  also gained `seedOpenPhase(harness, state)`, which writes the `status: 'running'` phase row DESIGN 4.2 E5 opens at
  every transition — the shape `seedIdleRun(… state: 'BUILD')` alone was missing, and the reason the old pause tests
  could not see the first blocker.
