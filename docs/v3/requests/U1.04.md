# Requests from U1.04

All of these are DESIGN clarifications that a fix round had to decide in order to close reviewer findings (R1-R3:
round 1; R4-R5: round 2; R4 was narrowed and R6 added in round 3). Nothing outside
`packages/security/{src,test}/exec/**` was touched; each item is a sentence DESIGN 2.6.6 could absorb so that
`U4.07` (L1 backends) and `U2.04` (tools write/exec) read the same rule the code implements.

## R1 — DESIGN 2.6.6 does not fix the order of the `ulimit` wrapper and `SandboxBackend.wrap()`

- **Where:** DESIGN §2.6.6, the L0 row (`ulimit -t/-f/-n/-u` through the constant wrapper) against the
  `SandboxBackend.wrap()` seam of the same section.
- **Why:** both rewrite `(file, args)`, and the composition is not stated. The blocker of fix round 1 was that
  `wrap()` was never called at all; wiring it required choosing a side.
- **What U1.04 did:** the sandbox wrap is applied FIRST and the `ulimit` wrapper goes around it —
  `sh -c '<ulimit script>' <backend argv...>` — so the rlimits also bound the sandbox helper process itself
  (`sandbox-exec` / `bwrap` and anything it forks before the real program starts). `wrap()` is documented as pure,
  so the opposite order stays possible if `U4.07` measures a reason for it.
- **Proposed change:** one sentence in §2.6.6: "the rlimit wrapper is the OUTERMOST layer; the backend's `wrap()`
  produces the argv it wraps."
- **Affects:** `U4.07`.

## R2 — a rlimit the kernel refuses: DESIGN says neither "fail" nor "degrade"

- **Where:** DESIGN §2.6.6 (`SandboxCapabilities.cpuTime` / `.processes`: `'enforced' | 'unavailable'`) and
  §7.4 S-24 ("bounded where `processes` is enforced, REPORTED otherwise — never silently skipped").
- **Why:** a `ulimit` the kernel refuses (a value above the hard limit) used to be swallowed by the wrapper's
  `;`-separated commands: the program ran with no limit while `guarantees` still said `enforced`, and the shell's
  own diagnostic was captured as the PROGRAM's output.
- **What U1.04 did:** the wrapper FAILS CLOSED. Each `ulimit` is `... 2>/dev/null || exit 126`, and `runOnce` maps
  exit 126 with zero output, when a rlimit was actually requested, to `outcome: 'error'`. The word `enforced` is
  then true by construction: either the limit is in force or there is no process. The alternative (degrade the
  reported `cpuTime`/`processes` to `'unavailable'` and run anyway) was rejected because it hands a caller a
  successful run under weaker isolation than it asked for.
- **Proposed change:** in §2.6.6, after the L0 row: "a requested rlimit the kernel refuses aborts the run
  (`outcome: 'error'`); `cpuTime`/`processes` never report `enforced` for a limit that was not applied."
- **Affects:** `U2.04` (it will see `outcome: 'error'` for an impossible `limits` value), `U4.07`.

## R3 — `ExecResult.outcome` for a program that simply failed

- **Where:** DESIGN §2.6.6 `ExecResult.outcome: 'ok' | 'error' | 'timed-out' | 'killed' | 'output-capped' |
  'sandbox-denied'`, which does not say which one a command exiting non-zero gets.
- **What U1.04 did:** `outcome` describes how the EXECUTOR ended the process. A program that ran to completion is
  `'ok'` whatever its exit code — the non-zero case is the caller's `tool-terminal/nonzero-exit`
  (`@cohorte/base` catalogue) — and `'error'` is reserved for a run that produced no usable process: an
  unverifiable cwd, a spawn failure, a refused rlimit (R2). Pinned by a test, since optimistic scheduling makes it
  a published contract.
- **Proposed change:** the same two sentences in §2.6.6.
- **Affects:** `U2.04`, `U3.05`.

## R4 — a program path containing `=` cannot go through the rlimit wrapper: L0 refuses it

- **Where:** DESIGN §2.6.6, the L0 row (`ulimit …` through the constant wrapper `/bin/sh -c '…; exec "$0" "$@"'`)
  and §0.2 I3.
- **Why:** the wrapper's last line execs through `/usr/bin/env -u PWD -u SHLVL` (macOS `/bin/sh` re-exports `PWD`
  and `SHLVL` into the environ on every `exec`, which `ExecRequest.env` and `OS_INJECTED_ENV` do not contain, so
  S-20 fails without it — `unset SHLVL` does not survive the `exec`, measured again in fix round 2). But `env`
  treats **any operand containing `=` as a variable assignment**, so a program path such as `/w/a=b/prog` is eaten
  as an assignment and `env` execs the NEXT argv element — a model-influenced argument (I3) — as the program.
  Measured on this machine (real `/usr/bin/env`, macOS):

  ```text
  $ /usr/bin/env -u PWD -u SHLVL "$PWD/a=b/prog" hello
  env: hello: No such file or directory        (exit 127 — it tried to exec the ARGUMENT)
  $ /usr/bin/env -u PWD -u SHLVL -- "$PWD/a=b/prog" hello   -> identical: `--` does not protect (BSD and GNU alike)
  ```

  There is no escaping form: assignments are operands, not options. **Arguments are not affected** — `env` stops
  scanning at the first operand without `=`, which is the program — and that is now pinned by a test.
- **What U1.04 did:** fail closed (I2). `isWrappableProgramPath(file)` (exported from `@cohorte/security/exec`)
  is `false` for a path containing `=`; `runOnce` then returns `outcome: 'error'` with **nothing spawned**, and
  names the refused path in `guarantees.notes`. The check is on the path the wrapper's `env` actually receives —
  `SandboxBackend.wrap()`'s output — so once `U4.07` prepends a sandbox helper, the original program is merely an
  argument of that helper and the restriction disappears for it.
- **The alternative that was rejected:** a second compile-time-constant script variant ending `exec "$0" "$@"`
  (no `env`) for such paths. It runs the program, but leaks `PWD` and `SHLVL` into the child, which breaks the
  S-20 invariant `visible ⊆ allow ∪ OS_INJECTED_ENV[platform]` — a security invariant traded for an exotic path
  shape. Refusing keeps every invariant true by construction.
- **NARROWED in fix round 3** (the second reviewer's own remedy, adopted): the wrapper exists to apply rlimits, so
  the executor now builds it ONLY when `requestsAnyRlimit(req.limits)` is true. A request with empty `limits` is
  spawned directly (`spawn(file, args, { detached, stdio })`), meets no `/bin/sh` and no `/usr/bin/env`, and is
  never refused; the refusal — and this R4 — survives only for a request that actually asks for
  `cpuSeconds`/`fileSizeBytes`/`openFiles`/`processes`. The direct path is not weaker: there is no shell, so I3
  holds by construction, and with no shell there is nothing to re-export `PWD`/`SHLVL`, so S-20 holds without a
  countermeasure (pinned by a second S-20 case that goes through the wrapper, and by an I3 case on each path).
- **Cost after the narrowing:** a project whose worktree path contains `=` runs its commands normally at L0, and
  loses only the rlimits — a `limits`-bearing call on such a path is still refused (`outcome: 'error'`). Before the
  narrowing the cost was every command of such a project.
- **Proposed change:** one sentence in §2.6.6 after the L0 row: "the rlimit wrapper is built only for a request
  that asks for a rlimit; a resolved program path containing `=` cannot be carried by it and such a request is
  refused (`outcome: 'error'`)." A gate-time refusal in `U2.04`'s `PathResolver` is still the nicer message, but it
  is no longer load-bearing: nothing else is refused now.
- **Affects:** `U2.04` (it will see `outcome: 'error'` only for a `limits`-bearing call on such a path), `U4.07`
  (the restriction lifts for a wrapped argv), `doctor`.

## R5 — `ExecResult.guarantees` carries per-REQUEST notes; `Executor.capabilities()` carries none

- **Where:** DESIGN §2.6.6 `SandboxCapabilities` ("[S] exactly what `cohorte doctor --json` prints under sandbox")
  against the plan's test "`ExecResult.guarantees` equals `probeSandbox()`" and the deliverable "`fs.readOnly`
  roots … L0 records them as advisory".
- **Why:** the two readings collide. `guarantees.notes` is the only place a result can record what L0 did **not**
  enforce for THIS call (the `fs.readOnly` / `denyRead` roots, the `native` shortfalls of a refusal), but
  `capabilities()` describes the MACHINE and is what `doctor` prints; a note about one call must not end up there.
- **What U1.04 did:** the executor now keeps `resolveSandbox`'s untouched report for `capabilities()` and mints a
  per-request copy for the result. So: `ExecResult.guarantees` equals `probeSandbox()` **for a request that asks
  for nothing L0 cannot deliver** (empty `fs.readOnly`/`denyRead`, and not a refusal), and otherwise equals it plus
  one note per thing recorded-but-not-enforced. `capabilities()` never accumulates a request's notes, and a cold
  `capabilities()` now reports the same `missing` as `probeSandbox()` (L1-binary detection is primed at
  construction and readable synchronously once settled).
- **Not recorded, deliberately:** `ExecRequest.network`. `SandboxCapabilities.network` already says `unenforced`
  at L0, and a note on every `network: 'none'` request would break the plan's `guarantees == probeSandbox()`
  assertion for ordinary calls.
- **Proposed change:** in §2.6.6, one sentence: "`guarantees` on a result is the probe report plus the notes that
  describe that request; `Executor.capabilities()` is the probe report alone." And, in `docs/v3/plan.json` /
  `PLAN.md`, this unit's `tests[3]` — still the unqualified "`ExecResult.guarantees` equals `probeSandbox()`" —
  becomes "`ExecResult.guarantees` equals `probeSandbox()` for a request that records nothing L0 cannot enforce".
  Both are outside this unit's `ownedPaths`; the narrowed equality is what the code and
  `test/exec/capabilities.test.ts` implement either way.
- **Affects:** `U4.07` (these notes are the seam it flips to enforced), `U3.05` / `doctor` (read `capabilities()`,
  not the last result).
- **Fix round 3:** the "readable synchronously once settled" half was not good enough — detection was primed
  asynchronously at construction, so a `capabilities()` in the same tick still answered `missing: []`. Detection is
  now fully SYNCHRONOUS (a few `stat`s: `accessSync('/usr/bin/sandbox-exec')` on darwin, a `PATH` scan for `bwrap`
  on linux, memoised per platform), so a cold `capabilities()` and `probeSandbox()` agree in the same tick. The
  spawned `which` is gone with it: `which` is not coreutils and is absent from many minimal Linux images, where it
  made `doctor` report `bwrap` missing on a host that has it.

## R6 — a child can outrun the executor's own setup: a note for every unit that spawns (information)

- **Where:** nothing in DESIGN; a defect found and fixed inside `packages/security/src/exec/executor.ts` in fix
  round 3, recorded here because two other units spawn children (`U1.07` runtime-pi, `U2.04`) and the trap is
  Node's, not this unit's.
- **What happened:** the executor attached its `'exit'` and `stdout`/`stderr` listeners AFTER `await`ing the
  `'spawn'` event and the `ps` fork that mints the start token (~10 ms). Node delivers `'exit'` once, to whoever is
  listening when it reaps the child, and discards a `stdout` that was never resumed — so a program faster than that
  fork (`/usr/bin/env`, `true`) lost ALL of its output and the `'exit'` event with it. Measured on this machine
  before the fix: `outputBytes: 0`, empty `tail`, and the run ending at its wall-clock timeout instead of at the
  program's exit (and never at all with a Clock that ignores `sleep`'s optional signal — R5's sibling finding).
  `node -e …` takes ~30 ms to start, which is why every existing test passed through it.
- **What U1.04 did:** every listener is wired synchronously, in the same tick as `spawn()`, before the first
  `await`; `escalate()` guards on a missing pid. Two tests pin it (`test/exec/lifecycle.test.ts`, "a program that
  exits before the executor finishes wiring itself up"), on the direct path and through the wrapper.
- **Affects:** nobody's contract. Worth one line in a gate report so `U1.07`/`U4.08` do not rediscover it.
