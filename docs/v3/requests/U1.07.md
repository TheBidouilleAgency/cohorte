# Requests from U1.07

## R1 — `AgentRuntimeProvider.authStatus / login / logout` have no port for the auth child's output

- **Where:** DESIGN §2.2.1 (`AgentRuntimeProvider`: only `create(bindings, pin)` receives `RuntimeHostBindings`) against
  DESIGN §3.2 / §3.7 layer 3 and this unit's first deliverable ("the child's stdout/stderr are PIPES that the parent
  line-buffers … and writes through the SEALED logger port into `host.log`, never a raw file: Pi can print refresh/login
  error bodies containing token material").
- **Why:** login and refresh are exactly where the engine prints a provider response body, and `ModelsError('oauth', …)`
  wraps any refresh failure (DESIGN 3.8). The auth child is spawned with the same `['ignore','pipe','pipe','ipc']` stdio
  as an agent's, but `authStatus`, `login` and `logout` are called on the PROVIDER, which holds no `RuntimeHostBindings`
  and therefore no `log` port. Until now those two pipes were drained and dropped, with a comment as the only record —
  the reviewer of fix round 1 was right to call that an unrecorded deviation.
- **What U1.07 did (fix round 1), without touching the contract:** `PiRuntimeProviderOptions` gained an optional
  `log?: RuntimeHostBindings['log']`; `createPiRuntimeProvider` threads it into `AuthChildSettings`, and `auth.ts` feeds
  both pipes through the same `drainChildOutput` + `seal.text` path an agent uses (64 KiB line cap, 1 MiB per exchange,
  `fields: { stream, source: 'auth-child' }`). With no `log` bound the pipes are still drained (an undrained pipe blocks
  the child) and the lines are dropped, exactly as before. Covered by
  `packages/runtime-pi/test/parent/parent-fake-brain.itest.ts` → "the auth child's output goes through the sealed
  logger, never to a raw file" (a token-shaped canary printed by the fake brain on stderr reaches the log only as
  `[REDACTED:canary]`).
- **Proposed change (lead's call, one of):**
  1. leave it as it is — the composition root (`apps/cli`, U4.x) passes `log` next to `redactor` when it builds the
     provider, and the guarantee holds for the CLI; or
  2. put the port in the contract: give `AgentRuntimeProvider.authStatus/login/logout` a
     `Pick<RuntimeHostBindings, 'log'>` parameter (or a `LoginInteraction.log`), so that "every child text is sealed and
     logged" is a requirement of the contract and not of one adapter's options. This changes
     `@cohorte/runtime-contract` and the fake runtime, hence the request rather than the edit.
- **Meanwhile:** option 1 is implemented and green; the composition root must bind `log` or the auth child's output is
  silently discarded (no leak either way: nothing is written unsealed, and nothing reaches a file).
- **Affects:** `U0.03` (contract) and whoever builds the provider in `apps/cli` (`U4.03` / `U4.05`).

## R3 — DESIGN 3.8 has no `auth.required.cause` for a 401/403 the PROVIDER pronounced (`rejected`)

- **Where:** DESIGN §3.8 (the `oauth` rows: `refresh-failed | expired | revoked`) and §3.7 layer 3 (the child's own
  pre-spawn check: `absent | mode-mismatch | ambient-source`) against
  `packages/runtime-pi/src/classify/index.ts` — a 401/403 with no engine code mints
  `provider-terminal/auth-required` with `details['auth.required.cause'] = 'rejected'`.
- **Why:** the two enumerations cover what the CHILD concludes before the run (no credential, wrong mode, ambient
  source) and what a refresh concludes (refresh failed, expired, revoked). A bare 401/403 on a model request is
  neither: the credential existed, was sent, and the provider refused it. `absent` would be a lie the human acts on
  (they would be told to log in when they are logged in and, for instance, out of entitlement), and `revoked`
  over-claims a fact nothing observed. Nothing types or schema-checks the key, so no consumer breaks either way —
  which is exactly why it must be written down rather than left to the reader (finding of fix round 2).
- **What U1.07 did (fix round 2):** kept `'rejected'`, documented it at its call site and pinned it with a classifier
  row (`test/classify/classify.test.ts`, "a 401/403 with no engine code is an AUTH_REQUIRED the provider itself
  pronounced"). Recorded under `deviations`.
- **Proposed change:** add `rejected` to DESIGN 3.8's enumeration ("`absent | mode-mismatch | ambient-source |
  refresh-failed | expired | revoked | rejected`, the last one for a 401/403 the provider itself answered"), or name
  the value the lead prefers and U1.07 renames it in one line.
- **Affects:** whoever switches on `auth.required.cause` (the AUTH_REQUIRED run effect, `doctor`, `auth status`).

## R4 — `SandboxPolicy` carries no `network.proxyEnv` flag, so `sandbox.env.allow` is the only channel for it

- **Where:** DESIGN §3.7 layer 1 ("… + proxy variables **only if `network.proxyEnv` is configured**") against
  `@cohorte/runtime-contract` §2.2.3 `SandboxPolicy` (`env: { allow, set }`, `network: { mode, allowHosts }` — no
  `proxyEnv`), and `@cohorte/config` `network.proxyEnv` (a `loosen` key, ADR-0026), which lives two layers away from
  `runtime-pi` and is never read by it.
- **What U1.07 did (fix round 2):** `childEnv` now enforces layer 1 itself instead of trusting the policy —
  `L1_ENV_ALLOW = ['PATH','HOME','LANG','LC_ALL','TZ','TMPDIR']`, plus `L1_PROXY_ENV` (`HTTP_PROXY`, `HTTPS_PROXY`,
  `NO_PROXY` and their lowercase spellings). A name in `sandbox.env.allow` outside that union is refused with
  `security/auth-mode-violation` **before any process exists**, as are loader names (`/^(LD_|DYLD_|NODE_)/i`) in
  `allow` and in `set`. The composition root's `network.proxyEnv` decision therefore reaches the runtime as the
  presence of the proxy names in `allow`: with the switch off they are simply not there.
- **Proposed change (lead's call, one of):** 1. leave it as it is and state in DESIGN 3.7 layer 1 that the proxy names
  in `sandbox.env.allow` ARE the `network.proxyEnv` decision; or 2. add `env.proxyEnv: boolean` to `SandboxPolicy` so
  the condition is carried explicitly and `childEnv` can refuse a proxy name when the flag is false (a contract
  change, hence the request rather than the edit).
- **Consequence for the composition root:** a `SpawnRequest` whose `sandbox.env.allow` names anything outside layer 1
  is now refused. The builder of the agent policy (`U3.x` / `U4.03`) must not forward project-chosen variables through
  `allow`; a host-chosen VALUE still goes through `env.set`, which is unrestricted apart from the credential and
  loader guards (nothing of the parent's environment travels that way).
- **Affects:** `U0.03` (contract), whoever builds `SandboxPolicy` from the config (`U3.x`, `U4.03`), `U4.07` (L1
  sandbox), and the S-40..S-46 security suite (`U5.02`).
