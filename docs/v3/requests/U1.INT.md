## R4 — pin verification is partial, and the hole is a security one: decide it at G2 or G3

- `docs/v3/requests/U1.10.md` D2, restated because it is the most consequential thing left open by Wave 1: DESIGN
  4.4 step 4 is implemented as `installInspector.installDir() === run.pinnedInstallDir` plus "the table version is
  shipped". **A pin tampered with IN PLACE — same install directory, different bytes — passes it**, which is exactly
  what ADR-0023 §3 and DESIGN 6.2 exist to catch. `InstallInspector.bundleManifest()` already exists, with nothing
  in `ResumeDeps` to compare it against.
- **Two answers, both fine, neither a gate's to pick alone:** (a) `ResumeDeps` gains `pins: PinReader` (and/or
  `snapshotter: RunSnapshotter`) and `checkImmutability` re-hashes the bundle manifest against the pin and verifies
  the run's snapshot manifest; or (b) DESIGN 4.4 step 4 states that the `dist/**` / snapshot re-hash is performed by
  the host launcher BEFORE `recover()` is called, and says where. `checkImmutability`'s shape survives both.
- **Why this gate did not pick:** both ports belong to a later wave's composition root, and (b) is a statement about
  a launcher (`apps/cli`, Wave 4) that does not exist yet. What a gate can do is refuse to let it go quiet.
- **Affects:** whichever unit owns full pin verification, `U4.01`, `U5.02`.

## R7 — every gate's exit check REBUILDS the gate build it declares immutable

- **Where:** `docs/v3/plan.json`, the `check` string of `U1.INT` (and the same shape in `U2.INT` … `U6.INT`), the
  matching "Done when" blocks of `docs/v3/PLAN.md`, against `docs/v3/gates/G1.md` §8 ("the gate build
  `.build/gate-1/` is immutable from now on. Wave-2 E2E units read it through `COHORTE_E2E_BUILD_DIR`; nothing
  writes into it again") and PLAN §3 rule 6 / §5 rule 4.
- **Why:** the check ends with

  ```sh
  … && node scripts/build.ts --out .build/gate-1 && node scripts/pack-check.ts .build/gate-1 && … checkpoint.ts G1
  ```

  so **the documented exit check is not re-runnable without rewriting the artefact Wave 2 is told to treat as
  frozen**. Anyone who re-runs it does: a reviewer verifying the gate, CI, `pnpm --reporter=silent unit:check U1.INT`.
  The U1.INT reviewer hit it during this review and clobbered `.build/gate-1` (`build: 28 asset file(s), 78 bundle
  file(s) -> …/.build/gate-1/.publish`). Nothing is lost when the rebuild comes from the same tree — but a Wave-2 E2E
  running against a directory that is being rewritten under it is a real race, and a gate document that promises a
  freeze its own command breaks is a gate document that lies.
- **Two answers, either fine, both the lead's:**
  1. **Scratch + publish.** Every gate `check` builds to a scratch directory — `node scripts/build.ts --out .build/gate-<n>-verify && node scripts/pack-check.ts .build/gate-<n>-verify` —
     and PLAN §5 rule 4 gains one line: the integrator publishes it to `.build/gate-<n>` **once**, by copy or link,
     after the check is green. The check then stays re-runnable for ever and the artefact is written exactly once.
  2. **Run-once check.** PLAN §5 states that a gate's exit check is run ONCE, by the integrator, and that every
     re-verification (reviewer, CI, `unit:check`) uses `--out .build/recheck-<n>`. Cheaper to write, but it makes the
     `check` string of `plan.json` something a reviewer must not run literally, which is exactly what `plan.json` is
     for.
- **Either way:** apply it to every gate row (`U0.G`, `U1.INT` … `U6.INT`) in `docs/v3/plan.json` and
  `docs/v3/PLAN.md`, then re-run `node scripts/gen-unit-checks.ts` (`--check` to confirm `tsconfig.checks/**` is
  still in sync — no `ownedPaths` change, so it should be).
- **Not done here:** `docs/v3/plan.json` and `docs/v3/PLAN.md` are not in U1.INT's `ownedPaths`, the decision binds
  five later gates, and a gate that rewrites its own exit check to make itself look re-runnable is the wrong party.
  `docs/v3/gates/G1.md` §8 now states the contradiction and names the interim workaround (`--out .build/recheck-1`).
- **Affects:** every gate from G2 on, every Wave-2+ E2E unit that reads `COHORTE_E2E_BUILD_DIR`, CI (`U6.INT`), and
  anyone re-running a gate's check.

## R8 — a COMPLETED run may carry a `tool.requested` with no `tool.completed`: pair on the EFFECT row

- **Where:** whoever CONSUMES a run's event stream — `tests/integration/protocol` (`U5.08`), the `status` renderer
  and its `--json` shape (`U4.03`/`U4.04`), any observer that pairs a tool call with its completion.
- **What:** after a crash inside the effect window (`tool.after-effect`), `Resumer` reconciles the `intent` row to
  `done` and the host that would have emitted `tool.completed` is gone; the replaying host must not invent one
  (`U1.10` D3). The run then reaches `COMPLETED` with **one `tool.requested`, zero `tool.completed`**, and an effect
  row whose `result` is the synthetic `{ reconciledBy: 'resume', at }`. Measured at this gate, on the real store:
  one of the eight crash cases produces exactly that shape, and `tests/integration/skeleton` now asserts the count
  by name (`hit.point === 'tool.after-effect' ? 0 : 1`) instead of permitting zero everywhere.
- **The obligation:** an unterminated `tool.requested` is **not** an error and must not be rendered, validated or
  asserted as one. The terminal fact about a tool call is its **effect row** (`state`, and `EffectRecord.result`
  read with D3's caveat), not the `requested`/`completed` event pair. A golden-NDJSON test that requires the pair,
  or a renderer that shows "still running", would be wrong about a run that is finished and correct.
- **Why it is filed rather than fixed:** nothing in the tree reads the pair today — `packages/core/src/state/evolve.ts`
  makes both types projection no-ops — so there is no code to change at G1, and the consumers do not exist yet.
  Recorded in `docs/v3/gates/G1.md` §3 (U1.10 D3 row) so it reaches them before they are written.
- **Affects:** `U5.08`, `U4.03`, `U4.04`, `U3.03`.
