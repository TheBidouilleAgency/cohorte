## D1 — `ResumeDeps` (frozen in `contract/factories.ts`, owned by U0.08) is under-specified for steps 9-11

- **Where:** `packages/core/src/contract/factories.ts`'s `ResumeDeps { store; clock; sweeper; effectVerifiers;
  worktrees }`, against DESIGN 4.4 step 9 ("Approvals: expire the due ones"), step 10 (the reconciliation note, and
  "an approved call is REPLAYED BY THE HOST before the note is built, through the `ToolHostReplay` port, DESIGN
  4.5") and step 11 ("Commit `run.resumed{mode:'recovery', report}`"), and step 4 ("the host's own install must be
  the pinned install... Mismatch ⇒ ... BLOCKED").
- **Why:** none of these are reachable with the five frozen fields. Writing `run.resumed` (and `lock.stolen`,
  `agent.state.changed`, `approval.resolved`, `repo.change.detected` along the way) needs an `EventWriter` to
  strict-validate, redact and seal a durable draft (DESIGN 2.5) — `StoreTx.appendEvents` only accepts an already
  `SealedEventDraft`, and only a `Redactor` mints `Sealed<T>` (check-layers rule f). Replaying an approved-but-
  unconsumed call needs `ToolHostReplay.replayApproved` (DESIGN 4.5): no other port can re-run stages 1-5 of the
  tool host on a stored call. Step 4's install-dir check needs `InstallInspector.installDir()`.
- **What this unit did:** widened `ResumeDeps` LOCALLY, in `packages/core/src/resume/index.ts` (an owned file, not
  `contract/factories.ts`) — PLAN §3 rule 7, "a unit that believes a contract is wrong ... continues against a local
  adapter". The five original fields are byte-identical; four are ADDED, each an EXISTING frozen port (no new
  contract, no new package edge): `events: EventWriter`, `redactor: Redactor` (seals the synthetic result
  `completeEffect` needs when a verifier proves an effect `'done'` with no fresh result of its own — DESIGN 4.1's
  verifier returns only a verdict, never a result value; see D3), `toolHostReplay: ToolHostReplay`,
  `installInspector: InstallInspector`. `createResumer`'s call signature (`(deps: ResumeDeps) => Resumer`) and the
  `Resumer`/`ResumeReport` shapes are UNCHANGED — only the deps object widens, exactly the pattern `EventsDeps` and
  `JournalDeps` already went through in U0.08's own fix round 1, except that widening happened inside U0.08's own
  file; this one could not, since `contract/factories.ts` is outside this unit's owned paths.
- **Proposed change:** widen the canonical `ResumeDeps` in `contract/factories.ts` to match (the additive fields,
  same names/types as above), so a later reader of the frozen contract sees the real shape and `@cohorte/core`'s
  barrel (`export { createResumer } from './resume/index.ts'`) and this file's export agree word for word.
- **Affects:** the G1 integrator (reconciling `contract/factories.ts`); the composition root that will eventually
  call `createResumer` for real (a later wave) needs to construct these ports, all of which already exist as
  frozen types today.
- **Status after fix round 1 (the reviewer raised the same point as a `lead` finding, and it still cannot be fixed
  from these owned paths):** a FIFTH additive field was needed to close the reviewer's step-6 / step-11 findings —
  `ids: IdSource` (`@cohorte/base`, already a frozen port), which mints the `ApprovalId` of the `blocked-ack`
  approvals DESIGN 4.4 steps 6 and 11 require. `ApprovalService` itself is deliberately NOT added: it would pull the
  whole approvals area in for one `putApproval`. So the widened set is
  `events: EventWriter; redactor: Redactor; toolHostReplay: ToolHostReplay; installInspector: InstallInspector;
  ids: IdSource`. The integrator's change in `packages/core/src/contract/factories.ts` is: (1) widen `ResumeDeps`
  with those five; (2) delete the `createResumer` stub body and delegate to `./resume/index.ts`, or keep the stub
  and have `resume/index.ts` `import type { ResumeDeps } from '../contract/factories.ts'` and re-export it (the
  U1.08 `EventsDeps` convention, `packages/core/src/events/index.ts:4-7`) — either way ONE `createResumer` in the
  barrel; (3) the Wave-0 "frozen barrel" test (lead note L3) currently passes only because `factories.ts` still
  refuses with `NotImplemented`, so it must be updated in the same change.
- **Status after fix round 2:** STILL OPEN and still not fixable from these owned paths; the second reviewer filed
  it as a `lead` finding with the sharpest statement of the consequence yet: `import { createResumer, type
  ResumeDeps } from '@cohorte/core'` today hands out a FUNCTION whose parameter needs nine fields and a TYPE that
  declares five, so the composition root (U4.01 / the G1 integrator) cannot type its deps object. Its prescription

## D2 — step 4 (immutability) implemented with `InstallInspector` only, not the full pin/snapshot re-hash

- **Where:** DESIGN 4.4 step 4: "the host's own install must be the pinned install (path + `dist/**` hashes), the
  snapshot digest must verify, the `RuntimePin` must verify, the table version must be shipped."
- **Why:** a full re-verification needs `PinReader` (re-hash CAS content) and `RunSnapshotter.verify(manifest)`
  (which itself needs a `RunSnapshotManifest` this port set has no way to load — the run row stores only a
  `snapshotDigest` and an opaque `runtimePin` JSON blob, not the manifest). Neither port is in the widened
  `ResumeDeps` (D1 already widens by the SMALLEST set steps 9-11 need; adding two more for a partial win seemed like
  the wrong trade).
- **What this unit did (fix round 1: `checkImmutability` is now SYNCHRONOUS — both halves read data already in hand,
  and it contained no `await`; it becomes asynchronous again the day a real `PinReader`/`RunSnapshotter` re-hash
  joins it):** `installInspector.installDir() === run.pinnedInstallDir` (exactly what ADR-0023 §2 says
  resume must check first: "the detached host is always spawned from that directory... after its hashes verify")
  plus `resolveTable(run.profile, run.tableVersion)` (U0.09, pure) for "table version must be shipped". Both
  failures map to `security/runtime-pin-mismatch`, `details.resumeRequires: 'reinstall-pinned-version'` — the same
  outcome DESIGN names for a pin mismatch. `packages/core/src/resume/immutability.ts`.
- **Proposed change:** when `PinReader`/`RunSnapshotter` are available to a later wave's composition root, widen
  `checkImmutability` (or add a sibling check the resumer also calls) for the hash/digest half; the install-dir
  check this unit ships stays correct either way, it just stops being the ONLY check.
- **Affects:** whichever later unit owns full pin verification (not yet assigned in the plan as far as this pack
  names); `docs/v3/gates/G1.md` should record that pin verification is partial until then.
- **Status after fix round 2 (raised again as a `lead` finding):** the reviewer states the residual hole precisely —
  "a pin that was tampered with IN PLACE (same install dir, different bytes — exactly what ADR-0023 §3 and DESIGN
  6.2 exist to catch) passes step 4 today" — and notes that `InstallInspector.bundleManifest()`
  (`packages/core/src/contract/ports.ts:86-89`) is already there, with nothing in `ResumeDeps` to compare it
  against. Its prescription, for the SAME commit as D1's widening: add `pins: PinReader` (and/or
  `snapshotter: RunSnapshotter`) to `ResumeDeps` and extend `checkImmutability` to re-hash `bundleManifest()`
  against the pin and verify the run's snapshot manifest — OR amend DESIGN 4.4 step 4 to say that the
  `dist/**`/snapshot re-hash is performed by the host launcher BEFORE `recover()` is called, and say where. Either
  answer is a G1 decision; `checkImmutability`'s shape survives both (it takes the extra port, or it does not).

## D3 — effect reconciliation writes a SYNTHETIC result for a verified-`'done'` effect

- **Where:** `StoreTx.completeEffect(id, result: SealedJson, post?)` demands an actual result value; DESIGN 4.1's
  `EffectVerifier.verify()` returns only `'done' | 'not-done' | 'in-doubt'` — no result payload (the table's
  "Verifier after a crash" column describes how the world is inspected, never what to store).
- **What this unit did:** `completeEffect(effectId, redactor.sealJson({ reconciledBy: 'resume', at: clock.now() }))`
  — a minimal marker. The ORIGINAL caller who needed the real result value is gone (that is the whole premise of
  recovery); what matters going forward is that the effect's STATE is `'done'` so nothing re-executes it, and the
  reconciliation note (step 10) narrates the outcome in words, not by replaying a stored JSON blob.
- **Proposed change:** none required; if a later reviewer wants the real result preserved, `EffectVerifier.verify`
  would need to return `{verdict, result?}` instead of a bare verdict — a contract change, not a fix here.
- **Affects:** any later code that reads `EffectRecord.result` off a resume-reconciled `'done'` row expecting the
  ORIGINAL tool result rather than this marker.
- **Status after fix round 2 (raised as a `lead` finding, and it upgrades this entry's "none required"):** the
  reviewer traced the consequence one hop further than this entry did — a later `EffectJournal.run()` on that
  idempotency key returns `{ status: 'replayed', result }` TYPED as the caller's `R` while actually holding the
  marker (a replayed `git.commit` hands back `{ reconciledBy: 'resume' }` instead of `{ sha }`), which DESIGN 4.1's
  own `verifiable` wording ("found ⇒ `done` with the RECONCILED result") does not sanction. Decide at G1, both
  options being outside this unit: (a) change `EffectVerifier.verify` to return `{ verdict; result?: JsonValue }`
  and have resume store the reconciled result, or (b) record in DESIGN 4.1 that a resume-reconciled `done` row
  carries a marker and that no caller may read `EffectRecord.result` of such a row as the original tool result.
  Nothing in this unit changes under either: it writes whatever the verifier gives it.

## D4 — `GitPort` has no generic "read a ref" primitive: `git.branch.create` / `git.ref.create` verified only for
worktree branches

- **Where:** `@cohorte/git/contract`'s `GitPort` (U1.05, green): `facts()` (per-worktree HEAD + branch),
  `findCommitByTrailer()`, and CAS/create operations — no `showRef` / `resolveRef`.
- **Why:** DESIGN 4.1's row for these two kinds says "ref at sha ⇒ done; elsewhere ⇒ conflict ⇒ BLOCKED", which
  needs reading an ARBITRARY ref (e.g. `refs/cohorte/<runId>/review/<n>`, never a worktree's own branch).
- **What this unit did:** `packages/core/src/resume/verifiers.ts`'s `refVerifier` reads the ref only when it
  happens to be a worktree's own branch (via `facts()`); otherwise it reports `'in-doubt'` — the conservative
  reading available to a port that can only answer `'done' | 'not-done' | 'in-doubt'` (it cannot itself raise the
  table's `conflict ⇒ BLOCKED`).
  **Fix round 1:** the code did not do what this entry said — a ref no worktree carried fell through to
  `return 'not-done'`, which the orchestration turns into `failEffect(interrupted)`, i.e. a blind re-execution of
  the ref-create; and the test that was supposed to pin it asserted the opposite of its own title. Corrected: the
  verifier now answers `'in-doubt'` for BOTH unreadable cases (no worktree carries the ref; the worktree branch sits
  at another sha, the table's "conflict"). It therefore never answers `'not-done'`, which matches DESIGN 4.1's row
  for these two kinds — it has no not-done column ("ref at sha ⇒ done; elsewhere ⇒ conflict ⇒ BLOCKED").
- **Proposed change:** add a read primitive to `GitPort` (`resolveRef(repo, ref): Promise<string | null>` or
  similar) so a bare ref can be verified without guessing. Out of this unit's owned paths (`@cohorte/git`).
- **Affects:** whichever unit eventually authors `git.branch.create`/`git.ref.create`'s `perform()` (worktree/mint-
  review-ref effects, not yet built) and registers a MORE PRECISE verifier for the bare-ref case; this unit's
  built-in verifier stays correct for the worktree-branch case either way.

## D5 — the `verify` JSON shape of the nine built-in effect kinds is this unit's own smallest-consistent reading

- **Where:** DESIGN 4.1's per-kind table names the DATA a verifier reads at intent ("target sha", "path, branch,
  base sha", "marker path", "host nonce", "manifest digest") but not the exact JSON keys, and no unit has yet
  authored the `perform()` that writes `EffectIntent.verify` for any of `git.branch.create`, `git.ref.create`,
  `git.worktree.add`, `git.commit`, `git.merge`, `git.worktree.reset`, `provision.command`, `agent.spawn`,
  `fs.snapshot.materialize` (all Wave 2/3 work: worktrees, provisioning, the agent supervisor).
- **What this unit did:** froze one JSON shape per kind, documented at each verifier function in
  `packages/core/src/resume/verifiers.ts` (e.g. `git.commit`: `{ repo, branch, key }`; `agent.spawn`:
  `{ pid, startToken, nonce }`; `fs.snapshot.materialize`: `{ manifestDigest }`).
  **Fix round 1:** `fs.snapshot.materialize`'s shape LOST its second field. It used to be
  `{ manifestDigest, runSnapshotDigest }` and the verifier compared the two — both written by the same producer in
  the same intent transaction, so the comparison could never detect the mismatch DESIGN 4.1 asks for, and the doc
  comment claimed a check against `RunRecord.snapshotDigest` that the code never performed. The run's own digest is
  now a DEPENDENCY (`BuiltinVerifierDeps.runSnapshotDigest: () => Sha256 | undefined`, supplied by whoever builds the
  registry), so the two operands come from different producers; with no digest available the verifier answers
  `'in-doubt'`. Whoever authors `fs.snapshot.materialize`'s `perform()` writes `{ manifestDigest }` only.
- **Proposed change:** whoever authors each kind's `perform()` matches this shape, or files a counter-request if a
  different shape is needed (e.g. because the intent side already has other data more natural to reuse) — either
  way it should be resolved before G2, since this unit's tests pin the shapes it expects.
- **Affects:** the worktrees/git effects unit, the provisioning unit, the agent supervisor unit (`U3.xx`, not yet
  assigned individual ids in this pack).

## D6 — step 9's inbox is surfaced, not interpreted: full command semantics are the engine's job

- **Where:** DESIGN 4.4 step 9: "pending commands are MAC-verified and applied in order (a `cancel` recorded while
  the host was dead wins here)."
- **Why:** interpreting a command (pause/resume/cancel/retry/skip/approve/deny) means running it through the
  transition table and guards (DESIGN 2.5.1) — that is the ENGINE's job (`RunEngine`, `U1.09`), not `Resumer`'s;
  `Resumer.recover()` returns a `ResumeReport`, which has no field for "here is what each command did", only
  `commandsApplied: CommandId[]`.
- **What this unit did (corrected in fix round 1):** the first implementation filled `commandsApplied` with every
  pending command id, which is a claim about work that never happened — no MAC was verified, nothing was dequeued,
  nothing was applied. `commandsApplied` is now `[]`, always: the field names the commands THIS procedure applied,
  and it applies none. What recovery does honour is step 9's own sentence, "a `cancel` recorded while the host was
  dead wins here": a pending `cancel` or `shutdown` HALTS the rest of recovery — no agent is reincarnated, no
  approved call is replayed — so the engine finds the run reconciled (steps 5-8) but not continued, and cancels it.
  MAC verification stays out of reach: it needs `CommandAuthenticator` **and** the project key (`KeyStore`), neither
  of which is in `ResumeDeps`, and applying a command means running the transition table and its guards.
- **Proposed change:** either the engine (U1.09) keeps the whole of step 9 — in which case DESIGN 4.4 step 9 should
  say so, and `ResumeReport.commandsApplied` is the ENGINE's field to fill after `recover()` returns — or
  `ResumeDeps` gains `authenticator: CommandAuthenticator` + `keys: KeyStore` and the resumer verifies (not applies)
  each pending command, reporting the verified ones. This unit picked the first reading: `Resumer` returns a
  `ResumeReport`, and the report has no field for "what each command did".
- **Affects:** `U1.09` (engine) / whichever unit wires the inbox into the transition table at resume time.

## D8 — `policy.inDoubt` is not reachable from this port set; recovery applies the DEFAULT (`ask`)

- **Where:** DESIGN 4.4 step 11's last sentence: "An `in-doubt` effect with `policy.inDoubt: 'ask'` (default) opens
  a `blocked-ack`-style approval before the agent continues."
- **Why:** the policy lives in the project configuration (`@cohorte/config`), which `ResumeDeps` cannot read, and
  the `runs` row does not carry it. The first implementation simply omitted the approval, which the reviewer caught:
  a run with an in-doubt at-most-once command continued silently under the default policy.
- **What this unit did (fix round 1):** when `ResumeReport.inDoubt` is non-empty, recovery opens ONE `blocked-ack`
  approval (`tx.putApproval` + an `approval.requested` draft through `deps.events`, one transaction, the event's own
  sequence as `requestedSeq`) before committing `run.resumed`, and adds it to `ResumeReport.approvalsCarried`. It is
  idempotent: the `idempotencyKey` is `apr:<runId>:blocked-ack:in-doubt`, so a second recovery reuses it. Its
  `preview.text` is the reconciliation note of step 10 — which is what puts that note in front of a human today
  (see D5's note about `Continuation.note` needing RunFiles/BlobStore). The DEFAULT `ask` is applied
  unconditionally: with no way to read the policy, refusing to ask would be the unsafe choice.
- **Proposed change:** carry the run's in-doubt policy on the `runs` row (it is frozen at start like every other
  immutability input), or hand a `policy` object to `createResumer`; then gate the approval on it.
- **Affects:** the config unit (U2.09) and the G1/G2 integrator.

## D9 — the same `blocked-ack` mechanism is how step 6's zone conflict reaches WAITING_APPROVAL

- **Where:** DESIGN 4.4 step 6: "A zone now held by another run ⇒ WAITING_APPROVAL(`conflict/zone-reserved`)".
- **What this unit did (fix round 1):** the first implementation recorded the failed acquisition as a string in
  `ResumeReport.locks.conflicts` and carried on to steps 7-11, committing `run.resumed` as if recovery had
  succeeded. Now a lock that cannot be rebuilt (a) HALTS step 10 — nothing is reincarnated, no approved call is
  replayed — and (b) opens a `blocked-ack` approval (`ruleId: conflict/zone-reserved`, key
  `apr:<runId>:blocked-ack:lock-conflict`). A pending blocking approval is exactly how a run reaches
  WAITING_APPROVAL in this architecture (`checkGlobalStops` ⇒ `approval-required` ⇒ T21), so the DESIGN outcome is
  reached without `Resumer` reaching into the transition table.
- **Also fixed here:** "rebuild locks" was implemented as "acquire if free", which could never succeed twice —
  `StateStore.acquireLock` refuses a conflicting row however stale its lease is, so the project / zone / integration
  / slot locks left behind by THIS run's own dead host made every second recovery report a conflict. A refusal whose
  single holder belongs to this run and whose `(pid, startToken)` is dead is now taken over with `stealLock`
  (fencing+1), the same way step 3 takes the run lease; only a holder that is another run, or one that is alive, is
  a conflict. That is DESIGN's own wording ("a zone now held by ANOTHER run").
- **Affects:** nobody else; recorded because it is a behaviour change visible in `ResumeReport.locks`.

## D11 — which effect kinds count as "a COMMAND effect" in step 8's quarantine bullet

- **Where:** DESIGN 4.4 step 8, second bullet ("unexplained, and the slot has a command effect that is `in-doubt` or
  `failed(interrupted)` ⇒ quarantine + reset") and ADR-0025 item 2, which repeats it; against DESIGN 4.1's kind
  table, which spells three different kinds with "command" in the name: `tool.run_command` (the agent's own
  command), `check.command` (the TEST sequence) and `provision.command`.
- **Why it matters:** this predicate is the border between a SECURITY signal and an automatic reset. The third
  bullet (`repo.change.detected` ⇒ `unexpected-repo-change` ⇒ BLOCKED) exists because something changed the tree
  that nothing explains; the second answers a change with `quarantineAndReset`, which throws away the agent's
  uncommitted work. ADR-0025 item 3's checkpoint cadence ("immediately before any `at-most-once` command executes —
  so a reset after an in-doubt command loses nothing but that command's own writes") bounds that loss **for an
  agent command only**; nothing makes the same promise for a `check.command` or a `provision.command`.
- **What this unit did (fix round 2):** `COMMAND_EFFECT_KINDS` in `packages/core/src/resume/index.ts` = exactly
  `{ 'tool.run_command' }`, with the DESIGN quote at its declaration. `check.command` always runs in `_integration`,
  which DESIGN 2.5.2 resets after every sequence (it is never a source of commits, so nothing of an agent's is at
  stake there), and `provision.command` writes dependency directories, not tracked worktree paths — neither is an
  agent's slot work, so neither buys a reset today. Before fix round 2 the predicate was `d.action !== 'done'` with
  no kind test at all: an interrupted `git.commit` / `git.worktree.add` / `agent.spawn` in the slot silently
  converted the unexplained-change signal into a reset (the second reviewer's PROBE B).
- **Proposed change:** name the set in DESIGN 4.4 step 8 (one clause: "a `tool.run_command` effect", or the wider
  list if the wider list is meant). If the wider reading is chosen, this is a one-line change to the constant plus
  the test that pins it (`packages/core/test/resume/recover.test.ts`, the two step-8 cases).
- **Affects:** the worktrees unit that authors `WorktreeService.quarantineAndReset`'s real body, and `U5.01`'s crash
  matrix (crash point #21).
