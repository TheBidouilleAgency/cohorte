# Requests from U0.02

## R1 — A crashed Biome exits 0: the lint step of every check can be green while nothing was linted (BLOCKER for trust in `unit:check` / `verify`)

- **Where:** `scripts/unit-check.ts` step 2 (`biome check`), root script `verify` (`biome ci .`), the CI `lint` job, and every
  unit's "Done when" that calls `pnpm exec biome ci <paths>`. Owner: `U0.01` / the lead. Nothing in U0.02's paths can fix it.
- **What happens:** Biome 2.5.14 is type-aware here because `nursery/noFloatingPromises` is an error. On some TypeBox
  shapes its type inference recurses without bound:

  ```text
  $ ./node_modules/.bin/biome ci packages/base packages/testkit ; echo rc=$?
  thread 'biome::workspace_worker_5' has overflowed its stack
  fatal runtime error: stack overflow, aborting
  rc=0
  ```

  The native binary dies on SIGABRT, and the launcher (`node_modules/.bin/biome`, so `pnpm exec biome` too) turns that
  into **exit code 0**. There is no `Checked N files` line and no diagnostic: the run LOOKS green. `biome check --write`
  behaves the same way, so a file that triggers the crash is also silently never formatted. Reproduced 100 % of the time,
  three runs out of three, on this machine (macOS arm64, Node 24.21.0).
- **How U0.02 found it:** its own check was green while four of its test files were unformatted and one source file had
  never been looked at. An exit-code bisect found nothing (every probe "passed"); only reading the OUTPUT did.
- **Proposed change (tooling):** treat the lint step as green only when the output carries Biome's summary line
  (`Checked <n> files`) AND does not contain `overflowed its stack` / `fatal runtime error`; fail otherwise, printing the
  paths. Same guard in `verify` and in the CI `lint` job. Until then, a unit should read the last line of its Biome
  output, not its exit code.
- **The trigger, as far as U0.02 characterised it** (bisected with throwaway probe files, all deleted):
  1. a RECURSIVE type that shares its NAME with an exported TypeBox const whose type Biome has to INFER, and
  2. something that makes Biome resolve that export: a class that `extends Error` holding a value of the type, a
     `typeof <const>` in a type position, or a namespace import (`import * as x`) of a barrel that re-exports it.
  - **The pure DESIGN §2 authoring convention triggers it** for a recursive union:
    `export const X = Type.Cyclic({ X: Type.Union([... Type.Ref('X') ...]) }, 'X'); export type X = Static<typeof X>;`
    crashes. So this is not specific to anything U0.02 chose; any later unit that authors a recursive `[S]` type can hit it
    (protocol snapshot trees, `EscalationStep`-like unions, finding trees...).
  - Non-recursive `[S]` types under the same-name convention are fine (`ModelRef`, `ErrorClass`, the id schemas: verified).
  - **Two remedies that work, both verified:** (a) give the const an EXPLICIT type annotation, so Biome has nothing to
    infer — `export const ErrorInfo: TUnsafe<ErrorInfo> = Type.Unsafe<ErrorInfo>(...)` keeps the DESIGN name and changes
    no contract; (b) give the schema const another name than the type.
- **What U0.02 did in its own paths:** `ErrorInfo` (`[S]`, name required by DESIGN) uses remedy (a); the JSON value
  schema uses (a) AND (b): it is exported as **`JsonValueSchema`**, because DESIGN 2.1 lists `JsonValue` as a type only
  (it is not `[S]`), so no contract moves. Both carry a comment saying the annotation must stay.
- **Affects:** every unit. `U0.03`, `U0.04`, `U0.05` first: they embed `ErrorInfo` and JSON values in payload schemas
  and declare error classes. A payload field holding arbitrary JSON is written `Type.Object({ result: JsonValueSchema })`
  (its static type is `JsonValue`).

## R2 — DESIGN 2.1 says the real IdSource is `crypto.randomUUIDv7`; it cannot be (information + one-line DESIGN fix)

- **Where:** DESIGN §2.1 `ports.ts` comment ("real: crypto.randomUUIDv7"), §11 / ADR-0017 (which cites it as a reason for
  the Node floor).
- **Why:** measured on Node 24.21.0: of 300 000 consecutive `crypto.randomUUIDv7()` values, 149 860 pairs are in
  DEScending order. It draws all 74 random bits afresh, so ids of one millisecond come out in random order, while PLAN
  U0.02 requires "uuidv7 ids monotonic per prefix" and ids are event / command / effect keys that must sort in minting
  order. `@types/node` 24.13.5 (the pinned one) does not declare the function either.
- **What U0.02 did:** `createUuidV7IdSource()` in `packages/base/src/ports.ts` is RFC 9562 method 2 (monotonic random)
  over `node:crypto` `randomFillSync`: strictly increasing across every id of one source, also while the wall clock
  stalls or steps back. Same wire shape (`<prefix>_<32 hex>`, version 7, variant 10).
- **Proposed change:** DESIGN 2.1 comment -> "real: monotonic uuidv7 (RFC 9562 method 2), base/ports.ts". The Node
  floor no longer depends on `randomUUIDv7`.
- **Affects:** nobody's code; `U0.06` / `U1.01` may rely on "ids of one source sort in minting order".

## R3 — `ID_PATTERN` alone is not ref-safe; `parseId` is stricter than the pattern (information)

- **Where:** DESIGN §2.1 ("Token-safe ... for refs and for paths"), §5.1 ("Every id passes `ID_PATTERN` before it reaches a
  path or ref").
- **Why:** `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,127}$` accepts `a..b`, `web.lock` and `web.`, which `git check-ref-format`
  refuses inside `cohorte/<runId>/<slot>/<n>`. Only free-form ids are exposed (`SpecId`, `SurfaceId`, brands of other
  packages); the prefixed kinds have exact shapes.
- **What U0.02 did:** `ID_PATTERN` is verbatim. `parseId` (and the exported `isSafeId`) additionally refuse `..`, a
  trailing `.` and a trailing `.lock`. A JSON Schema `pattern: ID_PATTERN` therefore accepts three shapes `parseId`
  refuses: a unit that takes a surface or spec id from a file (`U0.07` config / ownership / spec schemas) must still mint
  the brand through `parseId`, which DESIGN already demands ("the ONLY way to mint a brand from input").
- **Affects:** `U0.07`, `U1.05` (git), `U3.04` (worktrees).

## R4 — one catalogue code that DESIGN does not name: `validation/invalid-id` (information)

- **Why:** `parseId` returns `Result<Brand, ErrorInfo>` (DESIGN 2.1), an `ErrorInfo` needs a catalogue code, and no code
  of DESIGN 2.8 fits a malformed identifier. The catalogue is append-only, so adding is the cheap direction.
- **Proposed change:** add `/invalid-id` to the `validation` row of the DESIGN 2.8 table.

## R5 — notes for the units that build on base and testkit (information)

- `errorOf(code, ...)` takes the closed union `ErrorCode`, not `string`: a code missing from the catalogue is a COMPILE
  error in the unit that needs it. Ask for the row here (the catalogue is append-only; rows go at the end of their class
  block in `packages/base/src/catalogue.ts`); meanwhile `<class>/unexpected` exists for all thirteen classes.
- `toErrorInfo(e, fallback)` never emits a code outside the catalogue: `fallback.code` is used when it is a catalogue
  code of `fallback.class`, `<fallback.class>/unexpected` otherwise. It follows `Error.cause`, capped at 5.
- `NotImplemented` is a plain `Error`, not a `CohorteError`: reaching a stub is a bug, not a run outcome.
- `computeAnchorMac(key, runId, atSequence, chainHash)` signs the canonical JSON of
  `{ purpose: 'cohorte/chain-anchor/v1', runId, atSequence, chainHash }` (`ANCHOR_MAC_PURPOSE`). `U0.06`'s conformance
  suite and `U2.02`'s `CommandAuthenticator.anchor` call it; neither re-derives the body. Comparing two MACs
  timing-safely stays the caller's job.
- testkit: `import { test } from '@cohorte/testkit'` is vitest's `test` plus the per-test fixtures `tempDir`,
  `tempHome`, `tempRepo`; extend it with vitest 5's builder form
  (`test.extend('store', async ({ tempDir }, { onCleanup }) => ...)`). The first fixture argument MUST be an object
  destructuring pattern (vitest parses the source text), and Biome's `noEmptyPattern` forbids `({}, ...)`: destructure
  something, `task` if nothing else. Only the `temp-repo` area imports `vitest`; a Node CHILD process started by a test
  (fake brain, crash harness) imports `@cohorte/testkit/fixed-clock`, `/seq-ids`, ... — not the barrel.
- `GIT_ENV` / `gitEnv()` DROP every inherited `GIT_*` variable before adding the hermetic ones: a test run started from a
  git hook inherits `GIT_DIR` / `GIT_INDEX_FILE`, which would point every test at the developer's real repository.
