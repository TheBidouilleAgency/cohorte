## R4 — `biome.json` now excludes `schemas/` (G0-D5), which is a structural change a later integrator should know about

Biome's JSON formatter and `JSON.stringify(schema, null, 2)` disagree about arrays, so `biome ci .` and
`gen-schemas --check` each claimed the same bytes. `schemas` joins `tsconfig.checks` in the exclusion list.
If a later wave wants Biome to own that formatting instead, the change is in `serialize()`
(`scripts/gen-schemas.ts`) and it must stay byte-stable, because `--check` is a byte comparison.

## R5 — every gate unit's `check` in `plan.json` is red on its last step: it omits `COHORTE_CHECKPOINT_DIR`

- **Where:** `docs/v3/plan.json`, the `check` string of `U0.G` and of `U1.INT` (and of every later gate unit
  whose check ends the same way), plus the matching "Done when" block of `docs/v3/PLAN.md`.
- **Why:** the string ends in `node scripts/checkpoint.ts G0`. `scripts/checkpoint.ts` refuses to run without
  `COHORTE_CHECKPOINT_DIR` — by design, and as `PLAN.md` §3 rule 8, `plan.json` and `docs/v3/workspace.md`
  (§Commands) all require: a checkpoint is written OUTSIDE the repository, never inside it. So the literal check
  exits 2 in any shell that has not exported the variable:

  ```text
  pack-check: OK (…/cohorte-3.0.0-dev.0.tgz)
  checkpoint: COHORTE_CHECKPOINT_DIR is not set: checkpoints are written outside the repository, never inside it
  EXIT=2
  ```

  With the variable set, the same step is green (`checkpoint G0: 77 tracked change(s), 815 untracked file(s)`,
  exit 0). A reviewer, a CI step or a later gate that runs the recorded check verbatim therefore gets a red gate
  for a reason that has nothing to do with the work, and an implementer who sets the variable cannot honestly
  quote "the check as `plan.json` gives it".
- **Not this unit's to fix:** `docs/v3/plan.json` and `docs/v3/PLAN.md` are the lead's. `docs/v3/gates/G0.md` §8
  — which this unit owns — now prints the variable, which is the most a unit can do.
- **Proposed change:** prefix the LAST STEP — the one command that reads the variable — so that a bare run says
  what is missing instead of failing late:

  ```sh
  … && COHORTE_CHECKPOINT_DIR="${COHORTE_CHECKPOINT_DIR:?set an absolute dir outside the repo}" node scripts/checkpoint.ts G0
  ```

  A `check` string in `plan.json` is one line, which is why this is the form to put there.
- **NOT** `COHORTE_CHECKPOINT_DIR=<dir> pnpm --reporter=silent verify && … && node scripts/checkpoint.ts G0`.
  This file proposed that spelling in fix round 1 and the round-2 reviewer refused it, rightly: a POSIX/zsh
  assignment PREFIX applies to the single command it prefixes, not to the whole `&&` list, so `checkpoint.ts`
  never sees the variable and still exits 2 — the very failure this request is about. Measured on this tree:
  with the prefix, `pack-check: OK (…)` then
  `checkpoint: COHORTE_CHECKPOINT_DIR is not set: checkpoints are written outside the repository, never inside it`
  and `EXIT=2`; with `export COHORTE_CHECKPOINT_DIR=…` on its own line, the same last step prints
  `checkpoint G0: 77 tracked change(s), 815 untracked file(s)` and exits 0. `docs/v3/gates/G0.md` §8 now prints
  the `export` form, which is what a human runs by hand.
- **Affects:** `U0.G`, `U1.INT` (same shape, about to run), and every later gate unit. **Apply it to `U1.INT`
  before `U1.INT` runs**, in the `${…:?}` form only.

## R6 — `scripts/build.ts` runs `gen-schemas` in WRITE mode against the SHARED repository root

- **Where:** `scripts/build.ts:43` (`U0.10`'s owned path), in `runGenSchemasIfPresent()`:

  ```ts
  if (typeof generate === 'function') await generate({ repoRoot, check: false });
  ```

  called from `main()` as `await runGenSchemasIfPresent(REPO_ROOT)` — the repository root, never `<out>`.
- **Why it matters now:** PLAN §3 rule 6 says "No unit runs `pnpm build`, `tsc -b`, `gen-schemas` or `pack` …
  `schemas/` has one owner", and the same rule sends every unit to `node scripts/build.ts --out .build/<unit>/`
  for a private build. That step was inert while `scripts/gen-schemas.ts` did not exist (`build.ts` skipped it
  with a message, by design — `U0.10` R1). **This gate landed the script, so the step is now live:** from Wave 1
  on, any unit's private build silently rewrites `schemas/**` in the shared tree, and two concurrent private
  builds write the same files. `generateSchemas` in write mode also `rmSync`s every `.json` under `schemas/`
  that no source claims (`scripts/gen-schemas.ts:216-220`). It is harmless only while the committed schemas are
  already current — which is exactly not the case for a unit mid-edit of a TypeBox source, and is the one state
  the step exists to detect.
- **It also contradicts its own header:** `scripts/build.ts:4` documents step 1 as "gen-schemas (in memory …)",
  which `check: false` is not.
- **Proposed change** (the reviewer's, and the smallest one):

  ```ts
  const result = await generate({ repoRoot, check: true });
  // fail the build when result.ok === false, telling the operator to run `pnpm gen:schemas`
  ```

  That matches the header comment and DESIGN 1.4's "CI fails if `schemas/` is dirty": a build whose schemas are
  stale is a build that must not be published. If a real write is wanted for the PUBLISH build, gate it on
  `--out` being absent — a publish build writes the repository by definition, a `--out` build must not.
- **Why this gate did not make the change:** `scripts/build.ts` is `U0.10`'s owned path and is not a structural
  file (PLAN §3 rule 2). The gate build is green either way — the committed schemas are current, so the write is
  a no-op today — so no check of G0 is weakened by leaving it, and the honest record is a request rather than a
  silent edit of another unit's file. **It is a Wave-1 hazard, not a Wave-0 one: apply it before Wave 1 starts.**
- **Affects:** `U0.10` (owner), every Wave-1+ unit that builds privately, `U1.INT` and every later gate.
