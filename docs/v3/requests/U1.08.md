  of an `open` effect stays exactly where DESIGN puts it: `Resumer`.
- **Proposed change:** none needed for V3.0 as scoped; if a later wave wants `run()` itself to reconcile an `open`
  effect inline (skipping `Resumer`), that is a contract change to `EffectSpec`/`JournalDeps`, not a fix here.
- **Affects:** `Resumer` (`U1.10`) — it is the one that must call the per-kind verifiers of DESIGN 4.1's table.

## R6 — the frozen `EventWriter` cannot express DESIGN 2.3.2's ordering rule (BLOCKER for that deliverable)

- **Where:** `packages/core/src/contract/internal.ts` (`EventWriter`: `append(tx: StoreTx, drafts)` +
  `ephemeral(runId, e)`) against DESIGN 2.3.2 "Ordering rule under batching": "an ephemeral event is stamped at
  emission from the writer's queue, not at production: `EventWriter.ephemeral()` enqueues it behind every pending
  durable draft of the same agent and assigns `(sequence, sub)` only after that batch has committed — a producer
  that cannot wait flushes the batch first".
- **Why it cannot be done inside this unit:** `append()` is the writer's ONLY durable entry point and it is called
  synchronously INSIDE a store transaction. The <= 50 ms batch of DESIGN 4.2 E7 is assembled by the CALLER (the
  `AgentSupervisor`), so the writer never learns that durable drafts of an agent are pending; and `StoreTx` /
  `StateStore.transact` carry no commit hook, so the writer never learns when a batch actually committed. Every
  implementation of this port is therefore forced to stamp at production. Holding every ephemeral until the next
  `append()` instead is not a fix either: nothing durable is appended while a model streams, so the live token
  stream would stall for the whole message, and the first durable event after it would still commit AFTER the
  ephemerals were stamped.
- **Measured consequence (reviewer's probe, reproduced):** with message 1's durable drafts still pending, the deltas
  of message 2 are stamped `(0,1)`/`(0,2)` while `agent.message.completed` of message 1 commits at `(1,0)` — the
  exact outcome 2.3.2 forbids.
- **What this unit did:** (a) `ephemeral()` stamps against the last sequence the store is KNOWN TO HAVE COMMITTED,
  and `append()` reconciles that cursor with `runs.last_sequence` once per transaction before advancing it, so a
  rolled-back transaction can no longer leave the cursor permanently above the store (see the minor finding on the
  same port); (b) the test that claimed this coverage was renamed to what it actually asserts ("ephemerals emitted
  after a committed batch sort after it") and a test for the PENDING-batch case was added as `test.fails` — it runs,
  it demands today's failure, and it turns RED the moment a seam makes DESIGN's rule reachable; (c) the gap is
  documented at the `ephemeral()` implementation itself.
- **Proposed change (one of, lead's call at G1, to be recorded in `docs/v3/gates/G1.md`):**
  1. widen `EventWriter` with the batch seam DESIGN assumes — e.g. `enqueue(runId, drafts): void` +
     `flush(tx): DurableEnvelope[]` plus a commit signal, so the writer owns the pending batch; or
  2. add a post-commit callback to `StoreTx` / `StateStore.transact`, so the writer can move its cursor — and drain
     its ephemeral queue — on commit only; or
  3. restate DESIGN 2.3.2 so the ordering is the `AgentSupervisor`'s responsibility (flush the durable batch before
     emitting an ephemeral) and move the `tests/integration/protocol` assertion there.
- **Affects:** `U3.03` (AgentSupervisor, the producer), the `tests/integration/protocol` batched-run assertion, and
  this unit (the `test.fails` case flips to a normal test once the seam exists).

## R7 — `LeaseDeps` carries no host identity, yet `LockOwner` needs a real `(hostId, pid, startToken)`

- **Where:** `packages/core/src/contract/factories.ts` (`LeaseDeps { store; clock }`, frozen by U0.08) against
  `packages/persistence/src/contract.ts` (`LockOwner { runId?; hostId; pid; startToken }`) and DESIGN §2.4
  ("`startToken`: OS process start time: orphan kill never trusts a bare pid"), crash point #2 ("lease held by a
  dead `(pid, startToken)` => steal with `fencingToken + 1` after a liveness check") and DESIGN 4.4 step 3 ("live
  owner => `conflict/run-host-alive`; dead owner => `stealLock`").
- **Why:** recovery compares the STORED `(pid, startToken)` with the live process table. The previous
  implementation minted `startToken` from `clock.now()`, which matches no property of the process, so the liveness
  check could never be performed (a sweeper would always decide "dead" or always "cannot tell" — both violate I6).
- **What this unit did (fix round 1):** `startToken` is now the OS process start time,
  `String(Math.round(Date.now() - process.uptime() * 1000))` — exactly what a sweeper re-derives for a pid — taken
  from the REAL clock, never from `deps.clock` (a frozen test clock would reintroduce the defect). It is computed
  once per process and exported as `processStartToken()`. `createLeaseManager(deps, host?)` takes the run host's
  identity (`Pick<HostContext, 'hostId' | 'pid' | 'startToken'>`) as an OPTIONAL SECOND PARAMETER, because
  `LeaseDeps` is frozen and out of this unit's owned paths; the frozen one-argument call is unchanged.
  **DEVIATION:** without that argument the manager names itself `host:<pid>:<startToken>` from its own process —
  `pid` and `startToken` are then still exactly what the sweeper checks, but `hostId` is a stand-in, not the run
  host's id.
- **Proposed change:** widen `LeaseDeps` with `host: Pick<HostContext, 'hostId' | 'pid' | 'startToken'>` (the
  composition root already holds it: `RunEngine.run(runId, host)` / `Resumer.recover(runId, host)` are handed a
  `HostContext`), and drop the optional parameter; or state in DESIGN 2.4 that `LeaseManager` derives the identity
  itself, and say which. Record the decision in `docs/v3/gates/G1.md` so `U1.10` (Resumer) and the run host agree on
  what they compare.
- **Affects:** `U1.10` (Resumer / the orphan sweep), `U4.01` (run host, the composition root), `U0.08`'s file.

## R8 — DESIGN 4.3's crash points are per effect KIND; the journal now maps them, and two readings need confirming

- **Where:** `packages/core/src/durability/journal/index.ts` (`CRASH_FAMILY`) against DESIGN 4.3's table.
- **Why:** the journal is one code path, the registry is not. Firing `tool.after-intent` / `.after-effect` /
  `.after-done` for EVERY effect kind (what the previous implementation did) made `crashpoint()`'s per-NAME
  occurrence counter meaningless — a crash-matrix case targeting `tool.after-intent#3` would land inside a snapshot,
  a provisioning command or a merge — and left `transition-effect.after-intent` / `.after-external` never hit, which
  fails the crash suite ("a declared point never hit fails the suite").
- **What this unit did (fix round 1):** one family per `EffectKind`, total (`satisfies Record<EffectKind, …>`),
  exported as `crashFamilyOf(kind)` and pinned by `packages/core/test/durability/journal.test.ts`:
  `tool.*` and `check.command` -> `tool.after-intent` / `tool.after-effect` / `tool.after-done` (rows 12-13);
  `agent.spawn` -> `spawn.after-intent` / `spawn.after-ready` (row 9); `git.worktree.add` ->
  `provision.after-worktree-add`, `provision.command` -> `provision.after-install` (row 8); `git.commit` ->
  `commit.after-git-commit` (15); `git.merge` -> `merge.after-update-ref` (16); `git.worktree.reset` ->
  `reset.after-git-reset` (21); everything else -> the generic pair of row 6.
- **Two readings to confirm at G1:**
  1. **the generic pair.** DESIGN 4.3 row 6 (`transition-effect.after-intent` / `.after-external`) is read here as
     the journal's generic pair for an effect that has no kind-specific row — which is exactly what the transition
     effects of 4.2 E6 are (`create-integration-branch` = `git.branch.create`, `mint-review-ref` =
     `git.ref.create`), and what `fs.snapshot.materialize` and `git.worktree.remove` then also get.
     `snapshot.mid-materialize` (row 3) is NOT fired here: it is a point inside the materialiser's own loop, so
     `U3.02` owns it.
  2. **`check.command` in the `tool.*` family.** A check is a journaled command execution (DESIGN 2.5.2) with the
     same three positions; it is the only non-agent kind in that family.
- **Affects:** `U5.01` (crash matrix — it must find every declared point hit by the golden run), `U3.02` (the
  snapshot materialiser owns `snapshot.mid-materialize`), and any unit whose crash case names a point by
  `name#occurrence`.

## R9 — `EphemeralInput` carries no `source` and no `severity` (reviewer's `lead` finding, confirmed)

- **Where:** `packages/core/src/contract/types.ts` (U0.08's frozen file, NOT this unit's path):
  `EphemeralInput { type; payload; phase?; agent? }` against `EventDraftInput { …; source?; …; severity? }`.
- **Why it matters:** every ephemeral type of the catalogue originates in the runtime (`agent.message.started` /
  `.delta`, `agent.turn.started`, `tool.progress`), yet `EventWriter.ephemeral()` has no field to carry that, so
  `commonFieldsOf` defaults every ephemeral envelope to `source: 'cohorte'`, `severity: 'info'`, `summary: ''`.
  A durable twin written through `append()` (`agent.message.completed`) CAN be stamped `source: 'runtime'`, so a
  client grouping or filtering by `source` sees a message's deltas and its completion attributed to different
  producers; `severity: 'progress'`, which DESIGN 2.3.2 lists for exactly this kind of event, is unreachable.
- **What this unit did:** nothing — the type is outside `ownedPaths` and the defaults are the only reading available
  behind it. `ephemeral()` is written so that forwarding both fields is a one-line change once the type carries them.
- **Proposed change (one of, lead's call at G1):** (a) widen `EphemeralInput` additively to
  `{ type; payload; source?: 'cohorte'|'runtime'|'client'|'human'; phase?; agent?; severity?: … }` and have this unit
  forward both; or (b) record in `docs/v3/gates/G1.md` (and state in DESIGN 2.3.2) that ephemerals are deliberately
  always `source: 'cohorte'`, `severity: 'info'`, so `U4.02`'s observers and the protocol suite do not assume
  otherwise.
- **Affects:** `U0.08` (the type), `U3.03` (the producer), `U4.02` (observers), the protocol suite.

## Fix round 2 (independent review) — what changed

- **`packages/core/src/events/index.ts` (major, redaction failure).** The substitute event no longer reuses ANY
  free-form text of the draft that made the redactor throw: `summary` is now the constant
  `REDACTION_FAILED_SUMMARY` and `causationId` is dropped (`source`, `phase`, `agent` are host-minted and kept).
  Reusing the original `summary` meant that a secret in the summary — the agent-controlled human-facing string of
  DESIGN 2.3.6 — made the replacement throw on the same content and the exception escaped `append()`, rolling the
  caller's whole transaction back (inside `EffectJournal.run` that is tx A: no intent row, no effect) instead of
  degrading to `security/redaction-failed`. The substitute seal is additionally wrapped in its own `try/catch`: a
  redactor that also fails on a constant string and a two-literal payload cannot be sealed at all (I7), so that ONE
  draft is DROPPED — `append()` returns fewer envelopes — and the caller's transaction survives. Two tests added
  (`writer.test.ts`: the trigger in the summary; the doubly-failing redactor).
- **`packages/core/src/durability/lease/index.ts` (major, `onLost` after `stop()`).** `declareLost()` now returns
  early on `stopped` as well as on `lost`. A renewal already in flight when the caller stops the keeper (the normal
  shutdown: release the lease, then stop) used to answer `false` — the row is gone *because we released it* — and
  declare the lease lost, i.e. report a clean shutdown as a takeover. Two tests added (deferred renewal resolved
  `false`, and rejected, after `stop()`).
- **`packages/core/src/durability/journal/index.ts` (minor, swallowed error).** The `failEffect` transaction of the
  `perform()` failure path is now best-effort (`try/catch`) and the ORIGINAL error is always rethrown. Its usual way
  to reject is the lease having been stolen while `perform` ran, in which case the caller learned that the lease was
  gone and never what the tool failed with. The row then stays `intent`, which is what recovery reconciles by replay
  class (4.1). Test added (`journal.test.ts`: the lease stolen inside `perform` AND `perform` throwing).
- **`packages/core/test/events/writer.test.ts` (minor, `test.fails`).** The R6 case is a normal `test` again: it
  asserts TODAY's order positively (`compareOrder(completed, delta) > 0`, with the DESIGN-wanted `< 0` named in a
  comment). `test.fails` accepted ANY throw in the body — a slow `spooled()` timeout included — so it could have
  stayed green while covering nothing. It still turns red the moment R6's batch seam lands.
