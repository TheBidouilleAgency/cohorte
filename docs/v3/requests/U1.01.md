# Requests from U1.01

## R1 — `lead` severity: Biome's `noFloatingPromises` overflows the stack on plain, non-async code shaped around `RunRecord`

- **Where:** `biome.json` `linter.rules.nursery.noFloatingPromises` (owned by the lead). Reproduces on
  `packages/persistence/src/sqlite/tx.ts` (and smaller extracts of it, below) with the CURRENT `biome.json` unchanged.
- **What happens:** `pnpm exec biome check packages/persistence/src/sqlite` (or any invocation that includes
  `tx.ts`) sometimes exits with `thread 'biome::workspace_worker_N' has overflowed its stack / fatal runtime error:
  stack overflow, aborting`. **It is not code-shape-dependent in the way the lead's note suggested — it is not
  `packages/persistence/src/conformance/state-store.ts`, `src/memory/state-store.ts` or `test/contract/types.test.ts`
  only; it also fires on code that has nothing to do with those files.**
- **Minimal reproduction found** (no promises, no async, no class, no generics — 11 lines, isolated in a throwaway
  file outside any owned path and deleted before finishing):

  ```ts
  import type { RunRecord } from '../contract.ts';

  declare function readRun(): RunRecord;

  export function appendEvents(drafts: readonly string[]): number[] {
    let n = readRun().lastSequence;
    const appended: number[] = [];
    for (const _draft of drafts) {
      n += 1;
      appended.push(n);
    }
    return appended;
  }
  ```

  Removing the `for` loop, OR removing the `.push()` inside it, OR replacing `RunRecord` with a small inline object
  type all make the crash disappear. So: **a `for...of` loop that both reads a field off a value typed (transitively)
  through `RunRecord` before the loop AND calls `Array.prototype.push` inside the loop** is enough. `RunRecord` pulls
  in `runtimePin?: JsonValue` and `plan?: RunPlan` — `JsonValue` (`packages/base/src/json.ts`) is a `Type.Cyclic`
  (self-referential) type, which is my best guess at what the rule's resolver cannot terminate on; I did not chase it
  further into Biome's source.
- **It is FLAKY, not deterministic**, and that cost me time before I understood it: a direct shell invocation
  (`node node_modules/@biomejs/biome/bin/biome check --no-errors-on-unmatched <owned paths>`) crashed reliably across
  several tries; the SAME command run via `pnpm --reporter=silent unit:check U1.01` (which shells out through
  `scripts/unit-check.ts`'s `spawnSync(process.execPath, [biomeBin, ...])`, same arguments, same files) did **not**
  crash across 3 consecutive runs when I checked before finishing. I read this as a near-the-edge stack overflow
  whose outcome depends on the worker thread's incidental stack usage before it reaches the pathological recursion,
  not on anything about how it is invoked. **Do not treat a green `unit:check U1.01` as proof this is fixed** —
  it may recur under different load/thread-scheduling conditions (a whole-tree `biome ci .`, a different machine, a
  later Biome patch release changes nothing here since it is pinned exact).
- **Whether restructuring avoids it:** not usefully, for this file. The trigger (`for` loop + `.push` + a value typed
  through `RunRecord`) is `appendEvents`'s literal job — assigning a gapless gapless sequence to N drafts inside one
  transaction is inherently "loop, read a running counter derived from the run row, push a result". I confirmed the
  crash reproduces with `RunRecord` referenced ANYWHERE in the same file as such a loop, even with the loop and the
  `RunRecord` read completely unconnected (see the 11-line repro: `readRun()` is `declare`d, no `getRow` generic
  involved). Splitting `appendEvents` into its own file would only mean that file crashes as long as it also needs to
  read `run.lastSequence`/`run.lastHash`. The one workaround I found was **not touching `RunRecord` at all** in a file
  with such a loop, which is not available to `StoreTx.appendEvents` (its whole point is to write the run row's
  sequence and hash from a value it just read off `RunRecord`).
- **With the rule off** (checked with a local override config, never written into `biome.json`): `packages/persistence
  /src/sqlite/tx.ts` had one `lint/complexity/useOptionalChain` (fixed: `!row || row.status !== 'pending'` →
  `row?.status !== 'pending'`) and import-order/formatting only. Fixed. Nothing else was hiding behind the crash.
- **Affects:** any later unit whose owned files import `RunRecord` (or another type that embeds `JsonValue`/`ErrorInfo`
  — both are `Type.Cyclic`) into a file with a `for`/`.push` loop over it — plausibly common in `core`, `security`
  and anything driving the state machine. Flagging now so the lead can decide whether to disable the rule repo-wide,
  scope it away from `RunRecord`-shaped files, or wait it out; I made no change to `biome.json`.

## R3 — the conformance suite (`src/conformance/state-store.ts`, `src/conformance/fixtures.ts`) grew under me mid-unit; three of the new/tightened rules likely need the same fix in `memory/state-store.ts`

- **Where:** both files are untracked (`git status` shows `??`), owned by U0.06, and grew from 1275/191 lines (what I
  read at the start of this unit) to 1384/… lines by the time I finished — some other process amended them WHILE I was
  implementing, which the "optimistic scheduling" rule anticipates (my dependency may still be under review). I did
  not edit either file; I adapted `sqlite/**` to satisfy the version on disk when I ran the suite, per "code against
  DESIGN … do NOT fix it" — except here the file itself IS the moving target, so I coded against whatever the suite
  asked for at green time.
- **Three tightened rules I had to implement in `sqlite/**` that `memory/state-store.ts` (as I read it earlier in this
  session) does **not** yet enforce — if the SAME conformance suite now runs against the memory store too (it does,
  from `packages/persistence/test/memory/state-store.test.ts`), that suite is very likely red there for the same
  reasons, unless it was fixed in parallel:**
  1. **`putRun` in a run-scoped transaction must REWRITE an existing run, never CREATE one** (new test: "a run-scoped
     transaction may rewrite its run but never create one"). The version of `MemoryTx.putRun` I read only checked
     `r.runId !== this.#scope`, not that the run already exists.
  2. **A host-computed run column set to an explicit JSON `null` still counts as "not set"** (new comment + assertion
     in "a run row may leave IDLE only with the six host-computed columns set": `runtimePin: null` must be refused
     the same as an absent key, because `runtimePin?: JsonValue` makes `null` well-typed). The version of
     `assertHostColumns` I read checked `run[key] === undefined` only.
  3. **The fencing check must verify the lease's lock is the RIGHT kind for the scope being written** — `scope==='run'
     && key===runId` for a run-scoped transaction (or `scope==='project'` for a project one, in my reading of the new
     test's intent) — not merely "a lock exists with this id/token/host" (new test: "only the RUN lease writes the
     run: another lock of the same run is not a licence to write it", using a `zone` lock owned by the same host/run
     as the attack). The version of `MemoryStateStore.transact`'s lease check I read only compared
     `fencingToken`/`ownerHostId`, not `scope`/`key`.
  I implemented all three in `packages/persistence/src/sqlite/{tx,store}.ts`; my own conformance run (`test/sqlite/
  state-store.itest.ts`) is green against them. I did not implement them in `memory/**` — not my path.
- **A fourth thing that is a `sqlite/**`-specific consequence, not a `memory/**` one:** `LedgerEntry.sha256: Sha256 |
  null` (nullable, not optional) needed a one-column special case in my generic row-marshaller
  (`sqlite/marshal.ts`'s `NULLABLE_COLUMNS`) so that a SQL `NULL` becomes an explicit `null` for THIS ONE column
  (`worktree_ledger.sha256`) instead of an absent key like everywhere else. `MemoryTx` does not need this (it never
  serialises through columns at all), so there is nothing to compare there.
- **Proposed change:** the gate integrator re-runs `packages/persistence/test/memory/state-store.test.ts` against the
  conformance suite as it now stands and applies the same three fixes to `MemoryTx`/`MemoryStateStore` if it is red
  — I did not do this myself since `memory/**` is not in my `ownedPaths`.
- **Affects:** U0.06 / whoever owns `packages/persistence/src/memory/**`; the G1 integrator.
