## D6 — `COMMAND_MATRIX.skip` named a row id that does not exist (`T33`) — MAJOR, fixed

- **Where:** `packages/core/src/pipeline/command-matrix.ts`, the three `skip` cells (`active`, `suspended`, `failed`).
- **The defect:** the cells were `{ kind: 'transition', defId: 'T33' }`, but no table has a row with id `T33`: the
  skip rows are minted PER PHASE by `buildSkipRows` (`tables/shared.ts`, `id: \`T33-${target.phase}\``) because each
  one carries the entry effects of the success-path row it replaces. Every consumer that did what the cell said —
  look the id up in the run's table and fire it — would have got `undefined` for `skip` in all three profiles. The
  old matrix test could not catch it: it hand-mirrored the same literal `'T33'`, and nothing cross-checked matrix
  ids against the tables.
- **Fix (option (a) of the reviewer's two):** a new cell kind
  `{ kind: 'transition-per-phase'; defIdPrefix: 'T33-' }`, plus exported `SKIP_DEF_ID_PREFIX` and
  `skipDefIdFor(phase: ActivePipelineState): string`. The cell no longer names an id at all; the engine resolves the
  real row with `skipDefIdFor(phase)` — of the run's `resumeTo` in the suspended/FAILED columns, which is exactly
  DESIGN 2.5.1's "T33 if policy (on `resumeTo`)".
- **The missing assertion, added:** `test/pipeline/command-matrix.test.ts` now has, per table
  (`feature@1`/`bugfix@1`/`review@1`): every literal `defId` and every `mayTransition` the matrix names occurs
  EXACTLY ONCE among `table.rows.map(r => r.id)`; and, for the per-phase cell, every `skip-command` row's id equals
  `skipDefIdFor(row.from)` while no table holds a bare `T33`. Reverting the fix makes both fail.
- **Affects other units:** yes, favourably. `CommandMatrixCell` gained a member, so a consumer's `switch` over
  `cell.kind` must handle `'transition-per-phase'` — nobody consumes it yet (U0.09 is Wave 0; U1.09/U2.05/the CLI
  are the first readers), and the alternative was shipping a cell that names a non-existent row.

## D7 — a bare `'stop-rule'` always resolved to T24, leaving the SECURITY row T25-stop unreachable — MAJOR, fixed

- **Where:** `packages/core/src/pipeline/resolve-transition.ts`, the bare-reason branch.
- **The defect:** T24 (`*active -> WAITING_APPROVAL`) and T25-stop (`*active -> BLOCKED`) share
  `reason: 'stop-rule'`, a wildcard `from` AND an empty precondition list — DESIGN 2.5.1 separates them by the STOP
  REASON SET alone (T24: iteration-limit/budget-exhausted/timeout/identical-failure/no-progress; T25:
  policy-violation/unexpected-repo-change/runtime-incompatible), which `TransitionDef` has no way to encode as a
  `GuardId`. First-match-wins in table order therefore made T24 answer EVERY bare `'stop-rule'` from any active
  state but TEST (T16) and SHIP (T15), so a policy violation landed on WAITING_APPROVAL + `open-approval` instead of
  BLOCKED + `cancel-agents` + `freeze-worktrees`. `ReasonOrOutcome` accepts the bare reason, so nothing stopped a
  caller from taking the wrong branch.
- **Fix (the reviewer's: make the ambiguity impossible, not the caller's problem):** for `reasonOrOutcome ===
  'stop-rule'` the candidate set is narrowed to rows with a CONCRETE `from` (T15, T16, R07). If only
  wildcard-sourced rows match, `resolveTransition` now returns a new `{ ok: false, reason: 'stop-reason-required' }`
  instead of silently firing T24 — every wildcard stop row is reachable ONLY through the `{ stop: StopReason }`
  form, which already routes correctly through `STOP_ROW_MAPS`.
- **Tests added** (`test/pipeline/kernel.test.ts`): bare `'stop-rule'` from PREFLIGHT/BUILD/REVIEW/FIX is
  `stop-reason-required` and never T24; the concrete rows still answer the bare reason (TEST -> T16, SHIP -> T15);
  `{stop:'policy-violation'|'unexpected-repo-change'|'runtime-incompatible'}` reaches T25-stop -> BLOCKED from
  EVERY active state; the five T24 stop reasons still reach T24 -> WAITING_APPROVAL.
- **Affects other units:** `ResolveTransitionResult` gained a `{ ok: false; reason: 'stop-reason-required' }`
  member. A consumer that only tests `result.ok` is unaffected; one that exhaustively switches on `result.reason`
  must add the case. Nobody consumes it yet.

## D9 — `evolve`'s snapshot-cut test was a tautology — MINOR, fixed

# Fix round 2 — what the second reviewer found, and what changed

## D11 — `skip` from FAILED / a suspended state was unresolvable by the kernel — MAJOR, fixed

- **Where:** `packages/core/src/pipeline/resolve-transition.ts`.
- **The defect:** the matrix answers `{kind:'transition-per-phase', defIdPrefix:'T33-'}` for `skip` in the `*active`,
  `*suspended` AND FAILED columns (DESIGN 2.5.1: "T33 if policy (on `resumeTo`)"), but `resolveTransition` matched
  rows by `from` and every skip row carries a CONCRETE active `from`. Asking the kernel for a `skip` out of FAILED or
  PAUSED therefore returned `no-matching-row`, pushing every consumer to look the row up itself
  (`table.rows.find(id === skipDefIdFor(resumeTo))`) and to evaluate `policy.skip-allows` / `skip.justified` OUTSIDE
  the kernel — the guard bypass I10 exists to prevent. ADR-0018 §5 lists `skip` among the cells that must never be
  "impossible".
- **Fix (the reviewer's):** `ReasonOrOutcome` gains a third member `{ readonly skip: ActivePipelineState }` (the run's
  `resumeTo`), with a branch mirroring the existing `{ stop }` one: look the row up by `skipDefIdFor(skip)` and
  `evaluate` it. It deliberately does NOT re-check `matchesFrom` — that is the whole point: the run is parked while
  the row is sourced from the phase it would re-enter. A phase the profile does not let `skip` fire from simply has
  no such row and still answers `no-matching-row`.
- **Not done, on the reviewer's own advice:** no strict sibling row beside the wildcard — `resolveTransition` is
  first-match-wins over candidates sharing `(from, reason)`, so a lax wildcard would win after a strict row failed.
- **Tests added** (`test/pipeline/kernel.test.ts`): skip from FAILED and from every suspended state resolves
  `T33-<resumeTo>` with the right target; skip from the active phase itself resolves the same row; a missing
  `policy.skip-allows` is `guard-failed` on that guard, never a bypass; `{skip:'REVIEW'}` in `review@1` is
  `no-matching-row`.

## D12 — T30 never checked `auth.plan-satisfied`, so a human `resume` left AUTH_REQUIRED with auth broken — MAJOR, fixed

- **Where:** `packages/core/src/pipeline/tables/shared.ts`, `buildTailRows()`.
- **The defect:** DESIGN 2.5.1 conditions T30's extra guard on the SUSPENSION CAUSE ("plus
  `approval.none-pending-blocking` / `auth.plan-satisfied`"), while `command-matrix.ts` maps the WHOLE `*suspended`
  column of `resume` to the single id `T30`. The tail was split by REASON instead: `T30-auth` (which does carry
  `auth.plan-satisfied`) answers the SYSTEM reason `auth-restored`, a reason no `resume` command carries, so a human
  `resume` on an AUTH_REQUIRED (or QUOTA_EXCEEDED) run fired T30 and resumed with auth still broken.
- **Fix (the reviewer's "smallest fix", which keeps the matrix's single `T30` id and its published cell shape):**
  T30 carries BOTH extra guards, so the wildcard row is at least as strict as every suspension cause it covers.
  Resuming into an active phase with auth broken would in any case bounce straight back to AUTH_REQUIRED through T22,
  so nothing legal is refused. The per-state alternative was rejected because it would have had to reshape
  `CommandMatrixCell` a second time for a cell that already resolves correctly.
- **Consistency change made with it (not asked for, recorded here):** DESIGN 2.5.1 defines T31 as "T30 guards +
  `retry.target-legal`" and T32 as "`resume.acknowledged` + T30 guards", so both follow T30's list and gained
  `auth.plan-satisfied` too. A `retry` of a FAILED run and a `resume --ack` of a BLOCKED run both spawn agents.
- **Tests added** (`test/pipeline/kernel.test.ts`): `resolveTransition(FEATURE_V1, 'AUTH_REQUIRED', 'resume-command',
  <everything but auth.plan-satisfied>)` is `{ok:false, reason:'guard-failed', failedGuard:'auth.plan-satisfied'}`;
  the same from EVERY suspended state; all-pass still resolves T30 -> `*resumeTo`; T31/T32 are supersets of T30.

## D13 — `evolve` fabricated `run.version`, and never advanced `updatedAt` — MAJOR, fixed

- **Where:** `packages/core/src/state/evolve.ts`, the `base` fold.
- **The defect:** the fold did `version: state.run.version + 1` on EVERY event, while `appendEvents` bumps `version`
  once per CALL whatever the batch size (`memory/state-store.ts`: `if (drafts.length > 0) run.version += 1;`) and
  `records.ts` documents `version`/`lastHash`/`lastSequence` as store-assigned per transaction. Since `evolve` is
  exactly the "secondary reconstruction used for verification / resume audits" (its own header), a reconstruction
  could never be field-equal to the stored `RunRecord` for any run whose transactions append more than one event —
  and DESIGN 4.2's E5/E8 routinely do (`run.state.changed` + `phase.started`; `phase.completed` +
  `checkpoint.created`). `envelope.sub` cannot stand in for a transaction boundary: it is 0 for every durable event.
  `updatedAt` was never advanced either.
- **Fix:** `evolve` no longer touches `version` (nor `lastHash`, which it never set); both are documented in the file
  header as store-assigned per transaction and therefore excluded from any reconstruction comparison. `lastSequence`
  IS per-event and gapless and is still advanced; `run.updatedAt = envelope.timestamp` is now advanced too — the one
  clock field the stream can know.
- **Tests:** the `evolve.test.ts` spot check no longer asserts `version === 1` after one event (the wrong rule
  generalised); it asserts `lastSequence` and `updatedAt`, and a new case asserts that folding the whole nine-event
  stream leaves `version` and `lastHash` at their snapshot values while `lastSequence` reaches 9.

## D14 — `matchesFrom` resolved `*active` against the GLOBAL active set, not the table's own phases — MINOR, fixed

- **Where:** `packages/core/src/pipeline/tables/shared.ts`.
- **The defect:** a wildcard row fired from states the profile deliberately removed — `bugfix@1` (no BRAINSTORM/SPEC)
  resolved `T25-stop` from BRAINSTORM, `review@1` (phases TEST/REVIEW/FIX) resolved the whole T20-T27 tail from SHIP,
  PREFLIGHT and BUILD. The existing totality test only forbade a row TARGETING a state outside `phases`, so the
  property read stronger than it was.
- **Fix:** `matchesFrom(rowFrom, state, activePhases = ACTIVE_PIPELINE_STATES)`; `resolveTransition` and `nextStep`
  pass `table.phases`. `*suspended` is unaffected (no suspended state is ever a phase). `*any-non-terminal` (T27,
  `cancel`) is deliberately left global and excluded from the new assertion: `cancel` is legal from every
  non-terminal state by design, and narrowing it would be the one change that could make a run uncancellable.
- **Tests added** (`test/pipeline/tables.totality.test.ts`): per table, "no row is SOURCED from an active state
  outside `table.phases`" — for every row and every `PipelineState`, a covered state must be in
  `phases ∪ {IDLE} ∪ suspended ∪ halted`.

## D15 — a comment in `shared.ts` described a `review@1` skip row that does not exist — MINOR, fixed

`SkippablePhaseTarget`'s doc comment claimed "review@1's REVIEW skips straight to COMPLETED"; `review.v1.ts`'s
`SKIP_TARGETS` holds TEST and FIX only, and there is no `T33-REVIEW` row in that profile. The DATA is the defensible
reading (in `review@1` the verdict IS the product, so skipping REVIEW would make the run produce nothing), so the
comment was corrected to state the real rule. No data change.

## D16 — the "exit for every `PhaseOutcome` kind" test did not iterate `PhaseOutcome` — MINOR, fixed

The test carrying that name asserted only that each phase has a hand-declared exit in `EXIT_EXPECTATIONS` and that
each declared exit resolves; `PhaseOutcome`'s four kinds (`passed | failed | needs-human | suspended`) were never
walked, so nothing proved that e.g. a `failed` or `suspended` BUILD outcome has an exit. A new per-table `it` loops
the four kinds against every phase of `table.phases`: `passed` -> the profile's declared success reason, `failed` ->
`'tests-fail'` where a concrete row exists and otherwise the `{stop:'internal-error'}` T26 exit, `needs-human` ->
`'needs-human'`, `suspended` -> `{stop:'paused'}` (T20). The TEST-specific three-exit test is kept as the refinement
it already was. The property held before the fix (through the wildcard rows) — this makes a future narrowing of a
wildcard's `from` fail loudly instead of silently.
