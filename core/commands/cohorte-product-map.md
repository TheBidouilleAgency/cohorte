You are writing the **product map** of this repository: `PRODUCT.md` at the repo root. Its reader is the
product owner agent (and any person from the business): someone who must know **what the product already
does** — without reading code — before proposing a ticket. It is the business-side twin of `PIPELINE.md`,
which says how the repo is built.

> Read `.claude/profile.json` (the parsed `pipeline-profile` block; absent ⇒ that block in `PIPELINE.md`):
> `name`, `one_liner`, `project.kind`, `surfaces` (where each part of the product lives), `ui_language`
> (write the map in it). If `PRODUCT.md` exists, read it first: you are **updating** it — keep what is still
> true, correct what changed, add what is new, and do not rewrite sections that are still accurate.

## Discover — bounded

Use retrieval tools first when the profile has them, then Glob/Grep. Look for what a user can do, not how:
routes and pages, navigation and menus, API resources, CLI commands, scheduled jobs and emails, roles and
permissions, settings, integrations with outside services, `specs/*.md` with `status: merged` (features
already delivered) and `specs/_decisions.md` (product rules). Do not read whole files when a route table, a
router or a menu definition gives the list. Budget: about 40 reads.

## Write `PRODUCT.md` — ≤ ~200 lines

```markdown
# <Product name> — what it does

> Generated by /cohorte-product-map on <YYYY-MM-DD>. Read by the product owner agent. Keep it in business language.

## Who uses it
<the roles / kinds of users, one line each, and what each comes to do>

## What they can do
### <Area, e.g. Appointments>
- <a capability, as the user experiences it> — <who can, if restricted>

## Rules the product enforces
- <a business rule: limits, permissions, lifecycles, what is forbidden>

## Connected to
- <outside services, imports/exports, notifications>

## Known gaps
- <what is visibly missing or half-done — only what the code or the specs show>
```

No file paths, no technology names, no endpoints. A capability that only exists behind a flag or is half-built
goes under **Known gaps**, not **What they can do**.

Write the file (create or overwrite — it is a generated document, the source of truth is the code). Then end
with one line: the number of capabilities listed and the sections that changed since the previous version.
